# 注文内容の変更（暗27）— 設計

「注文リストの行の【変更】を押したら何が出るか」を決めた。**Figma のみ。実装は未着手。**

---

## いまどうなっているか

行が `<details>` で開き、中に **−／個数／＋／削除** が出るだけです。

**足りないもの**

- **トッピングを外せません。** チーズを付けたのをやめたくても、
  いったん削除して入れ直すしかない
- **選び直せません。** 米粉そば → 米粉うどん、たこ焼きのお味なども同じ
- **「削除」が重複しています。** 行の左端に「−」を置いたので、
  同じことをする口が 1 行に 2 つある

---

## どうするか

**【変更】を押したら、品を選んだときと同じモーダルが開く。**
違うのは、いまの選択が最初から入っていることと、ボタンが「変更を保存」であること。

**Figma: 暗27 注文内容を変更する（モーダル）**（`395:4050`、x=5109 y=2000）

### なぜ同じモーダルにするのか

**やることが同じだからです。** 「麺を選んで、トッピングを選んで、個数を決める」——
追加のときと 1 つも違いません。同じ作業に別の画面を作ると、覚えることが増えます。

行の中に開く形（いまの `<details>`）も考えましたが、
**390px の行に選択肢 6 つ＋必須の組＋個数は入りません。**
入れると行がとても高くなり、下の品が画面の外へ出ます。

### 中身

| | |
|---|---|
| 写真の帯 | **213 → 140 に詰めた**（下記） |
| 品名と価格 | そのまま |
| **麺の変更（必ず 1 つ）** | **新しく足した**。丸いボタン。いま選んでいるほうが入っている |
| トッピング（任意） | 四角いチェック。付けているものが入っている。箱の中がスクロール |
| 数量 | そのまま。−／数／＋ と、その内容での金額 |
| ボタン | やめる ／ **変更を保存　¥1,510** |

### 決めたこと

**写真を 213 → 140 に詰めました。**
変えに来た人がほしいのは操作の場所で、写真は「この品で合っている」の確認でしかありません。
控えた 73px を選択肢に回しています。

**「必ず 1 つ」の組は丸、「いくつでも」の組は四角。**
形が違えば、読まなくても選び方が分かります。
四角が 2 つ並んでいると、両方選べるように見えます。

**ボタンは「変更を保存」。**「注文に追加」のままだと、
押すともう 1 行増えるように読めます。

## 部品について

`暗/選択肢の行`（`170:3519`）には `状態=未選択／選択中` しかなく、**形の指定がありません**。
暗27 では、麺の変更の 2 行だけ角丸を 4 → 12 に上書きして丸くしています。

この形を続けるなら、**部品に `形=四角／丸` を足すのが本筋**です。
上書きのままだと、行を足すたびに手で丸くすることになり、必ず忘れます。
実装に移すときに一緒に直してください。

## 実装するときに要るもの（未着手）

**画面だけでは終わりません。サーバ側に足すものがあります。**

- いまの `/cart/update` は **key と個数しか受け取りません**。
  選択肢を変える口がない
- カートの行の key は **商品 ID ＋ 選択肢 ID から作られています**
  （`CartLine.buildKey`）。**選択肢を変えると key も変わります。**
  つまり「その行を書き換える」ではなく
  「古い行を消して、新しい行を入れる」になる
- そのとき**同じ内容の行が既にあると、まとまります**（`Cart.add` の仕様）。
  チーズ入りを 2 行持っていて片方のチーズを外したら、
  素のほうと 1 行にまとまる。**これは正しい動きですが、
  画面上は「行が消えた」ように見えます。**
  そう見えてよいか、確かめてから実装すること

## 一緒に片付くこと

**行の中の「削除」を消せます。** 行の左端の「−」と役割が重なっているので、
変更のモーダルに移った時点で不要になります。
