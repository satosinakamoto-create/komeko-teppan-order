# バックアップと復元

最終更新: 2026-08-17

---

## 何が・いつ・どこに取られるか

| 項目 | 内容 |
|---|---|
| 取られるもの | DB 全体（注文・伝票・会計・メニュー・卓・スタッフ）＋商品画像 |
| 中身 | `database.zip`（H2 の `BACKUP TO` による整合コピー）＋ `uploads.zip` |
| タイミング | ① 毎日 4:30（定時） ② 起動時の追いつき（前回から20時間以上空いていたら） ③ アプリ終了時 ④ 管理画面の「今すぐバックアップ」 |
| 保存先 | `backups\20260817-043000\` のような日時フォルダ（設定 `app.backup.dir`） |
| 世代管理 | 最新 14 世代を残して古いものは自動削除（設定 `app.backup.keep`） |
| 2次コピー | `app.backup.extra-copy-dir` にパスを入れると同じものをもう 1 か所へ複製 |

設定はすべて `src/main/resources/application.yml` の `app.backup:`。

### 知っておくべき制限

- **定時（4:30）は、その時刻に PC とアプリが動いているときだけ走る。**
  クラウドのサービスではなくアプリ内のスケジューラなので、
  PC の電源が落ちていれば（スリープでも）何も起きず、逃した回の再実行も無い。
  その穴を埋めるのが「起動時の追いつき」で、前回のバックアップから
  20 時間以上空いていれば起動した瞬間に 1 本取る。
- **電源を直接切ると「終了時バックアップ」は走らない。**
  ただしデータ自体は DB のトランザクションで守られており、
  翌日の起動時追いつきがそれを含めてバックアップするので、実害は
  「電源断からその追いつきまでの間にディスクが壊れた場合」に限られる。
- **同じ PC の同じディスクに置いたバックアップは、ディスク故障には無力。**
  `extra-copy-dir` に **USB ドライブか OneDrive のフォルダ**を指定すること。
  これを設定して初めて「二重」になる。
- PostgreSQL で運用する場合、この仕組みは対象外（管理画面にもその旨表示される）。
  `pg_dump` の夜間実行か、クラウド managed DB の自動バックアップを使う。

## 復元手順

> ⚠️ 復元は「いまのデータを過去の状態で上書きする」操作です。
> 管理画面からはできないようにしてあります（誤操作の被害が最大級になるため）。
> 以下を落ち着いて、順番どおりに。

1. **アプリを停止する**（起動している PowerShell で Ctrl+C）

2. **いまのデータを退避する**（すぐ消さない。復元をやり直せるように）

   ```powershell
   cd C:\Users\zaki\projects\komeko-teppan-order
   Rename-Item data\komeko.mv.db komeko.mv.db.broken-20260817
   ```

3. **戻したい世代を選ぶ** — `backups\` の中から日時フォルダを選ぶ
   （フォルダ名が新しいほど最近。迷ったら一番新しいもの）

4. **DB を戻す** — 選んだフォルダの `database.zip` を展開すると
   `komeko.mv.db` というファイルが出てくるので、`data\` に置く

   ```powershell
   Expand-Archive backups\20260817-043000\database.zip -DestinationPath data\
   ```

5. **画像を戻す**（`uploads.zip` がある場合）

   ```powershell
   Expand-Archive backups\20260817-043000\uploads.zip -DestinationPath data\uploads\ -Force
   ```

6. **起動して確認する**

   ```powershell
   .\tools\run.ps1
   ```

   管理画面でメニュー・注文履歴・伝票がその時点まで戻っていることを確認。
   **バックアップ以降の注文は当然含まれない**ので、紙の控えなどから手で補う。

7. 問題なければ、手順 2 で退避した `.broken-*` ファイルは数日置いてから削除してよい。

## 復元の練習の記録（2026-08-30 実施）

**この手順で実際に戻せることを確認済みです。** 以下は実施の記録。

### やったこと

本番データを壊さないよう、**隔離したフォルダに復元**して、そこへアプリを向けて起動した
（手順 2 の「いまのデータを退避」の代わりに、そもそも別の場所へ展開した）。
戻したのは `20260826-180519` — わざと**古い世代**を選び、
「数日前のバックアップを、今日のコードで開く」という現実の事故に近い形にした。

```powershell
# 隔離した場所へ展開（本番の data\ には触れない）
Expand-Archive backups\20260826-180519\database.zip -DestinationPath <作業用>\data\
Expand-Archive backups\20260826-180519\uploads.zip  -DestinationPath <作業用>\data\uploads\ -Force

# そこを向いて、別ポートで起動する
.\.tools\apache-maven-3.9.9\bin\mvn.cmd spring-boot:run `
  "-Dspring-boot.run.arguments=--server.port=8081 --spring.datasource.url=jdbc:h2:file:<作業用>/data/komeko;DB_CLOSE_ON_EXIT=FALSE --app.upload-dir=<作業用>/data/uploads --app.backup.enabled=false --app.seed-on-startup=false"
```

`--app.seed-on-startup=false` と `--app.backup.enabled=false` を付けるのが要点。
前者を忘れるとサンプルデータが戻したデータに混ざり、後者を忘れると練習が本番の世代を 1 つ食う。

### 結果

| 見たもの | 展開直後 | アプリ起動後 |
|---|---|---|
| テーブル数 | 13 | **17** |
| 注文 | 21 件 | 21 件（保持） |
| 伝票 | 15 件 | 15 件（保持） |
| 商品 | 94 件 | 94 件（保持） |
| 税率マスタ | なし | 3 行（自動投入） |
| 控除率マスタ | なし | 5 行（自動投入） |

zip はどちらも手順書どおりフラットに展開され、アプリは 3.6 秒で起動、`/ping` も 200。
**手順書は正しい。** 画像 3 枚も一緒に戻った。

### 分かったこと

- **古い DB × 新しいコードは、dev では問題なく開ける。**
  在庫モジュールを作る前（13 テーブル）の DB でも、`ddl-auto: update` が
  足りない 4 テーブルを補い、税率・控除率マスタも自動で入った。
  ただし**本番（PostgreSQL）は `validate` + Flyway なので挙動が別物**になる。
  本番で古い世代に戻すときは、Flyway の適用状況とコードの版を合わせる必要がある。

- **終了時バックアップは「正常終了」でしか走らない。**
  `Stop-Process -Force` で落としたときは走らなかった（実測）。
  スタートメニューからのシャットダウンなら通常は走るが、
  電源ボタン長押しやコンセントを抜く運用では走らない。
  一度、いつもの落とし方で `backups\` が増えるか確かめておくとよい。

- 復元そのものより、**アプリを別の場所・別ポートへ向ける引数を組み立てるほうが手間**だった。
  上のコマンドを控えておけば、事故当日に考えることが減る。

## 動作確認のしかた（復元の練習）

事故が起きてから初めて復元するのは怖いので、**一度練習しておくことを強く勧めます。**

1. アプリを起動してテスト注文を 1 件入れる
2. 管理画面 → バックアップ → 「今すぐバックアップを取る」
3. さらにテスト注文をもう 1 件入れる
4. 上の復元手順を実行する
5. 「2 で取った時点」に戻っていること（3 の注文が無いこと）を確認する
6. 練習が終わったら `data\` を消して初期状態からやり直してもよい
