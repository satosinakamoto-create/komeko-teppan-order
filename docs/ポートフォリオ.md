# ポートフォリオへの載せ方

このシステムを職務経歴・ポートフォリオサイトに載せるための、素材の作り方と文章のたたき台。

**この文書の要点**：機能を並べても差はつかない。**「何を防いだか」を書く**と一気に変わる。
素材はすでに全部そろっている（このリポジトリのコミット履歴が証拠になる）。

---

## 1. 何を見せるか

見せたいのは「連携」なので、**1 つの画面に 2 端末を並べた GIF** が最強。
スマホ単体の GIF と厨房画面単体の GIF を別々に置くと、
**見る人が頭の中で繋げないといけない**ので伝わらない。

```
┌──────────────────┬───────────────────┐
│  スマホ（お客さま） │  PC（厨房ボード）   │
│  QR → 注文確定     │  ← 同じ瞬間に届く   │
└──────────────────┴───────────────────┘
```

動画ではなく **GIF** を勧める理由。

- 再生ボタンを押させない（押されなければ、無いのと同じ）
- スマホで見ても止まらない
- ページに複数並べられる

## 2. 撮る手順

### 準備（1 回だけ）

```powershell
# 1. 撮影用のデータを入れて起動する（厨房ボードが埋まる／在庫の残数も映る）
.\tools\run.ps1 -Demo

# 2. 別の窓で、スマホと厨房画面を左右に並べる
.\tools\demo-screens.ps1
```

`-Demo` は次をやる。**撮影に使う「カウンター1」だけは空けておく**ので、
そこで実際に QR を読んで撮る。

- ほかの 3 卓に伝票を作る（厨房ボードの「受付／調理中／提供待ち」3 列が埋まる）
- 在庫の残数を設定（残り 3 個・2 個・5 個）
- 1 品を売り切れにする（押せないボタンも見せどころ）

> `-Demo` は **dev プロファイル＋環境変数**の両方がそろったときだけ動く。
> 本番ではクラス自体が読み込まれないので、実データに架空の注文は混ざらない。
> すでに開いている伝票があるときも投入を見送る（何度実行しても積み上がらない）。

`demo-screens.ps1` は scrcpy でスマホ画面を PC のウィンドウとして出し、
その隣に厨房ボードを開いて左右に並べる。
録画は Windows の **[Win]+[Alt]+[R]**（Xbox Game Bar）で画面全体を撮ればいい。

### 撮る 3 本

| # | 内容 | 長さ | 何が伝わるか |
|---|---|---|---|
| 1 | QR → 人数 → メニュー → 注文確定 → **厨房に出る** | 15 秒 | システムの核。これだけで「作れる人」だと分かる |
| 2 | 厨房で「調理中→提供済」→ **スマホの伝票が勝手に変わる** | 10 秒 | SSE のリアルタイム連携。技術的な見どころ |
| 3 | ホールで会計 → **深夜料金・チャージの内訳** | 10 秒 | 業務理解。ここが他の学習用作品と決定的に違う |

**3 番目を必ず入れること。**
ログイン付き CRUD は誰でも作る。深夜料金を注文時刻で判定する、打ち直しの救済がある、
という話は**実店舗の運用を聞いて作った証拠**になる。面接で必ず掘られる。

> 深夜料金を映すには、店舗設定で開始時刻をいまの時刻より前にする。
> **撮り終わったら 23:00 に戻すこと。**

### GIF にする

10MB を超えると読み込みで待たされる。幅 900px・15fps に落とせば 2〜3MB に収まる。

```bash
ffmpeg -i rec.mp4 -vf "fps=15,scale=900:-1:flags=lanczos,split[a][b];[a]palettegen[p];[b][p]paletteuse" out.gif
```

ページに置くときは `loading="lazy"` を付け、**ファーストビューは静止画**にする。
最初に見えるものが GIF だと重く感じる。

## 3. 文章のたたき台

### 見出し

> **米粉と鉄板 モバイルオーダー**
> 実店舗（学芸大学の居酒屋）のために作った、卓番 QR のセルフオーダーシステム

### 概要（3 行）

> お客さまが席の QR を読み、自分のスマホから注文する。
> 注文は同じ瞬間に厨房のボードへ届き、状態を進めるとお客さまの伝票にも反映される。
> テーブルチャージ・深夜料金・消費税を含む会計まで、一連の流れをすべて扱う。

### 技術構成

| | |
|---|---|
| 言語・基盤 | Java 21 / Spring Boot 3.3.5 |
| 画面 | Thymeleaf ＋ 素の CSS・JavaScript（フレームワーク不使用） |
| DB | H2（ファイル DB）／本番想定は PostgreSQL |
| 認証 | Spring Security（管理者・スタッフの権限分離） |
| リアルタイム | SSE（Server-Sent Events） |
| テスト | JUnit 5 ＋ AssertJ ＋ MockMvc（266 件） |

## 4. ここが本番 —— 「防いだ事故」で書く

機能の羅列と、事故を防いだ話。同じ内容でも読後の印象がまるで違う。

> ❌ 深夜料金の自動計算、在庫管理、リアルタイム更新を実装しました
>
> ✅ 下記

そのまま貼れる形で書いてある。**全部このリポジトリのコミットに残っている実話。**

### 深夜料金は「会計時刻」ではなく「注文時刻」で決まる

> 当初は会計時刻で伝票全体に割増をかけていました。
> しかしそれでは、22 時に注文を終えたお客さまが 23 時過ぎまで話し込んだだけで
> 全額に 10% が乗ってしまいます。逆に 23 時半に注文して朝に帰れば割増ゼロです。
> 店主に確認したところ実際の運用は「注文した時刻で決まる」だったため、
> 注文 1 件ずつ判定する形に作り直しました。
> 同じ伝票の中に通常料金と深夜料金の注文が混在します。

**続けて書くと強い（副作用まで考えた証拠）**

> この変更には副作用がありました。店側のミスで注文を取り消して入れ直すと、
> 注文時刻が新しくなり、お客さまには何の落ち度もないのに 10% が乗ります。
> そこで明細ごとに割増の対象から外せるようにしました。
> **注文時刻そのものは書き換えません。**「いつ厨房に入ったか」は提供時間の集計にも使う
> 事実の記録なので、事実は残し、判断（割増を取るか）だけを別の項目として持たせています。

### テストが 266 件すべて通っても、起動できないことがある

> 設定項目を増やしたとき、テストは全件通ったのに実際のデータベースでは起動しませんでした。
> Hibernate の `ddl-auto: update` は、**すでに行が入っているテーブルに NOT NULL の列を足せません**。
> 既存の行に何を入れるか決められないからです。
> テストは毎回まっさらな DB を作るため「無いテーブルを作る」経路しか通らず、
> この失敗は原理的に検出できませんでした。
> 以後、スキーマを変えたら必ず実データの入った DB で 1 回起動して確かめています。

### 「動くはず」で終わらせず、動かない理由を切り分ける

> スマホから開けない問題に半日かかりました。ping は通るのに 8080 番だけ届かない、
> という切り分けにくい症状で、原因は Windows ファイアウォールに残っていた
> Java への「拒否」ルールでした。**ファイアウォールは拒否が許可より常に強い**ため、
> 正しく許可を作っても効きません。ICMP はプログラムと無関係なので素通りし、
> Java が待つポートだけが落ちる、という現象になっていました。
> 以後、同じ回り道をしないよう Tomcat のアクセスログを有効にして、
> 「サーバまで届いているか」を一目で二分できるようにしています。

### 見えている不具合の裏に、別の原因があることがある

> メニューのタブが上に固定されない問題で、最初はヘッダーの高さが原因だと考えて直しました。
> それでも直らず、本当の原因は `position: sticky` の性質でした。
> **sticky は親要素の箱の中でしか貼り付きません。**
> タブを包む要素がタブと同じ高さしかなく、貼り付く余地が 0 だったのです。
> 症状が同じでも原因は別、という良い例でした。

### ログを埋める警告を放置しない

> `AsyncContext` の警告がログを埋めていました。
> 画面を閉じる・タブを切り替える、といったごく普通の操作で
> リアルタイム通信の接続は切れます。その切れた接続へ書き込もうとしていたのが原因でした。
> 実害は「ログが読めなくなる」ことですが、それは**本当のエラーを見逃す**という意味です。
> 接続ごとに生存フラグを持たせ、送る前に確認するようにしました。

## 5. 面接で聞かれたら

**「いちばん難しかったところは？」**

> 金額です。1 円でも多く請求すれば信用を失い、少なければ店が損をします。
> しかも間違いはその場では誰も気づかず、数日後にレジ締めが合わないという形で出てきます。
> だから計算は 1 箇所（`TableSession.recalculate`）にまとめ、
> 単価・税率は注文時点の値をコピーして保存し、
> あとから設定を変えても過去の伝票が動かないようにしました。

**「テストは何を書きましたか？」**

> 266 件のうち、いちばん厚いのは金額の計算です。
> 切り捨ての向き（お客さまに有利に）、キャンセルした注文の扱い、
> 同じ品を 1 回で頼んでも 2 回に分けても金額が変わらないこと、などを固定しています。
> 最後のものは、注文ごとに切り捨てると「分けて頼んだほうが安い」抜け道ができるためです。

**「1 人で作ったんですか？」**

> はい。ただし業務ルールは店主に確認しています。
> 深夜料金の判定を会計時刻から注文時刻へ作り直したのも、確認して違いが分かったからです。
> 想像で作らないこと、が今回いちばん学んだことでした。

## 6. 載せるときのチェックリスト

- [ ] GIF は 3MB 以下・幅 900px 以下
- [ ] ファーストビューは静止画（GIF は `loading="lazy"`）
- [ ] 2 端末が 1 つの画面に写っている
- [ ] 深夜料金の内訳が読める大きさで写っている
- [ ] 「防いだ事故」を最低 2 つ書いた
- [ ] リポジトリを公開する場合、**個人情報・鍵が無いことを確認**
      （このリポジトリは private 前提。公開するなら別途棚卸しが必要）
- [ ] 撮影後、店舗設定の深夜料金の開始時刻を 23:00 に戻した
- [ ] 撮影後、デモの伝票をホール画面から会計して片付けた
