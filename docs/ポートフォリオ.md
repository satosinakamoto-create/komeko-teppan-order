# ポートフォリオへの載せ方

このシステムを職務経歴・ポートフォリオサイトに載せるための、素材の作り方と文章のたたき台。

**この文書の要点**：機能を並べても差はつかない。**「何を防いだか」を書く**と一気に変わる。
素材はすでに全部そろっている（このリポジトリのコミット履歴が証拠になる）。

---

## 0. まず結論 —— 公開デモがいちばん強い

GIF より強い素材がある。**その場で触れる本物**が公開されている。

| | |
|---|---|
| **公開 URL** | https://komeko-teppan-order.onrender.com/login |
| **入り方** | 「**ゲストで参加する**」を押すだけ（ID もパスワードも不要） |
| リポジトリ | https://github.com/satosinakamoto-create/komeko-teppan-order（public） |
| 稼働 | Render / Docker / 無料枠。平日 8〜17 時は起こしてある |

> ⚠ **ルート URL（`/`）はお客さま側の入口**で、「席の QR を読んでください」と出る。
> 見学者に案内するのは必ず **`/login`** のほう。

### 訪問者にたどらせる道

```
「実際に触ってみる」を押す
   ↓
ログイン画面 →「ゲストで参加する」
   ↓
厨房ボード（すでに 6 件の注文が並んでいる）
   ↓
左メニュー →「QRコード」→「この卓のお客さま画面を開く」（別タブ）
   ↓
注文する → 元のタブの厨房ボードに、リロードなしで届く
```

タブを 2 つ並べれば 1 台の PC で連携が体感できる。
スマホで QR を読んでもらえれば実店舗とまったく同じ体験になる。

### 書き添えておくこと（書かないと減点に見える）

> 無料枠のため、しばらく誰も触っていないと最初の 1 回だけ 30〜40 秒かかります。

これを書いておかないと「重いサイト」と誤解される。書いてあれば「制約を理解して選んでいる」に変わる。

## 1. 何を見せるか

見せたいのは「連携」なので、**1 つの画面に 2 端末を並べた GIF** が最強。
スマホ単体の GIF と厨房画面単体の GIF を別々に置くと、
**見る人が頭の中で繋げないといけない**ので伝わらない。

```
┌──────────────────┬───────────────────┐
│  スマホ（お客さま） │  PC（厨房ボード）   │
│  QR → 注文確定     │  ← 同じ瞬間に届く   │
└──────────────────┴───────────────────┘
```

動画ではなく **GIF** を勧める理由。

- 再生ボタンを押させない（押されなければ、無いのと同じ）
- スマホで見ても止まらない
- ページに複数並べられる

## 2. 撮る手順

### 準備（1 回だけ）

```powershell
# 1. 撮影用のデータを入れて起動する（厨房ボードが埋まる／在庫の残数も映る）
.\tools\run.ps1 -Demo

# 2. 別の窓で、スマホと厨房画面を左右に並べる
.\tools\demo-screens.ps1
```

`-Demo` は次をやる。**撮影に使う「カウンター1」だけは空けておく**ので、
そこで実際に QR を読んで撮る。

- ほかの 3 卓に伝票を作る（厨房ボードの「受付／調理中／提供待ち」3 列が埋まる）
- 在庫の残数を設定（残り 3 個・2 個・5 個）
- 1 品を売り切れにする（押せないボタンも見せどころ）

> **⚠ 撮る日に実行すること。**
> 厨房ボードは「その日の営業日」ぶんしか表示しない。
> 前の日に入れたデモデータは、営業日の切り替え時刻（5:00）をまたぐとボードから消える。
> 実際、深夜 3:39 に作ったデータが翌朝 11:39 には 1 件も出なかった。
> バグではなく仕様どおりの動きなので、**撮る直前に走らせる**。

> `-Demo` は **dev プロファイル＋環境変数**の両方がそろったときだけ動く。
> 本番ではクラス自体が読み込まれないので、実データに架空の注文は混ざらない。
> すでに開いている伝票があるときも投入を見送る（何度実行しても積み上がらない）。
> 見送られたときは、ホール画面（`/hall`）で全部お会計してから実行し直す。

`demo-screens.ps1` は scrcpy でスマホ画面を PC のウィンドウとして出し、
その隣に厨房ボードを開いて左右に並べる。
録画は Windows の **[Win]+[Alt]+[R]**（Xbox Game Bar）で画面全体を撮ればいい。

### 撮る 3 本

| # | 内容 | 長さ | 何が伝わるか |
|---|---|---|---|
| 1 | QR → 人数 → メニュー → 注文確定 → **厨房に出る** | 15 秒 | システムの核。これだけで「作れる人」だと分かる |
| 2 | 厨房で「調理中→提供済」→ **スマホの伝票が勝手に変わる** | 10 秒 | SSE のリアルタイム連携。技術的な見どころ |
| 3 | ホールで会計 → **深夜料金・チャージの内訳** | 10 秒 | 業務理解。ここが他の学習用作品と決定的に違う |

**3 番目を必ず入れること。**
ログイン付き CRUD は誰でも作る。深夜料金を注文時刻で判定する、打ち直しの救済がある、
という話は**実店舗の運用を聞いて作った証拠**になる。面接で必ず掘られる。

> 深夜料金を映すには、店舗設定で開始時刻をいまの時刻より前にする。
> **撮り終わったら 23:00 に戻すこと。**

### GIF にする

10MB を超えると読み込みで待たされる。幅 900px・15fps に落とせば 2〜3MB に収まる。

```bash
ffmpeg -i rec.mp4 -vf "fps=15,scale=900:-1:flags=lanczos,split[a][b];[a]palettegen[p];[b][p]paletteuse" out.gif
```

ページに置くときは `loading="lazy"` を付け、**ファーストビューは静止画**にする。
最初に見えるものが GIF だと重く感じる。

## 2.5 公開デモの設定

実際の手順は [デプロイ.md](デプロイ.md) にある。ここでは考え方だけ。

公開デモは `demo` プロファイルで動かす。**既定はすべて無効**なので、実店舗では何も起きない。

| 設定 | 何が起きるか |
|---|---|
| `app.guest-login` | ログイン画面に「ゲストで参加する」が出る |
| `app.demo-data` | 起動時に営業中の状態が作られる（開いている伝票が無いときだけ） |

### ゲストで参加する

押すと**スタッフ権限**で厨房ボードに入る。

| | 画面 |
|---|---|
| **見える** | 厨房ボード、ホール（会計）、品切れ・残数、ダッシュボード、**QRコード**、商品、カテゴリ、卓、店舗設定、スタッフ、売上、注文履歴 |
| **見えない** | バックアップのみ |

方針は **「GET は全部開ける・POST は一切通さない」**。
最初は見せる画面を選んでいたが、それだと作ってあるものの大半が伝わらなかった。

**この切り分けが成立するのは、管理画面が
「表示はすべて `@GetMapping`・変更はすべて `@PostMapping`」に
きれいに分かれているから。** GET で状態が変わる口が 1 つでもあれば使えない手で、
実際に全 Admin コントローラを確認してから決めている。

バックアップだけは GET も閉じてある。サーバ上の保存先パスと世代一覧が出るうえ、
デモではバックアップ自体を止めているので見せる中身がない。
**サイドバーにもリンクを出していない**（入口と許可は必ず一致させる）。

**QR コードの画面がいちばん効く。**
卓名・QR 画像・URL がすべてこの 1 画面に載っているので、
「どうやって注文が始まるのか」がここだけで伝わる。
訪問者はこの画面から実際にお客さま側を開ける。

**見える画面でも、書き換えは一切できない。** `POST`（QR の再発行・設定の保存・
商品の削除）はすべて 403 になる。
ただし 403 を出すだけでは不親切なので、画面側でも
**上部に「見学モードです」の帯を出し、保存・削除ボタンを押せなくしてある**。

> **守ることと、伝えることは別の仕事。**
> Security が弾くので「安全」ではある。けれど押せてしまうと、
> 押した人はエラー画面に飛ばされて「壊れている」と受け取る。

**注文を進める・キャンセルするのは、あえてできるようにしてある。**
押してもらえないと連携が体感できないため。荒らされてもデータを入れ直せば戻る。

> **管理者アカウントは公開しないこと。**
> ゲストは見るだけだが、管理者は本当に書き換えられる。
> 荒らされても実害は無い（実店舗とは別の DB で、再起動で作り直される）が、
> 見に来た人が壊れた画面を踏むのは避けたい。
> パスワードは `INITIAL_ADMIN_PASSWORD` に入れて Render の画面にだけ置く。

技術的な作りは 3 段構え。

1. `@ConditionalOnProperty` で、無効なら**コントローラ自体が存在しない**（URL を直接叩いても 404）
2. GET ではなく **POST ＋ CSRF**。リンクにすると外部サイトに
   `<img src=".../login/guest">` と書かれるだけで、見に来た人が勝手にログイン状態になる
3. 付く権限は `STAFF` のみ

### スリープ防止（`/ping`）

無料ホスティングは無通信が続くとサーバを眠らせ、次に開いた人が 30〜40 秒待たされる。
`/ping` は `ok` とだけ返す軽い入口なので、外から定期的に叩いて起こしておく。

**アプリの中にタイマーを置いても無意味。** 眠っている間はそのタイマーも止まっている。
外部のサービス（UptimeRobot / cron-job.org）から叩くこと。

## 4. ここが本番 —— 「防いだ事故」で書く

機能の羅列と、事故を防いだ話。同じ内容でも読後の印象がまるで違う。

> ❌ 深夜料金の自動計算、在庫管理、リアルタイム更新を実装しました
>
> ✅ 下記

そのまま貼れる形で書いてある。**全部このリポジトリのコミットに残っている実話。**

### 深夜料金は「会計時刻」ではなく「注文時刻」で決まる

> 当初は会計時刻で伝票全体に割増をかけていました。
> しかしそれでは、22 時に注文を終えたお客さまが 23 時過ぎまで話し込んだだけで
> 全額に 10% が乗ってしまいます。逆に 23 時半に注文して朝に帰れば割増ゼロです。
> 店主に確認したところ実際の運用は「注文した時刻で決まる」だったため、
> 注文 1 件ずつ判定する形に作り直しました。
> 同じ伝票の中に通常料金と深夜料金の注文が混在します。

**続けて書くと強い（副作用まで考えた証拠）**

> この変更には副作用がありました。店側のミスで注文を取り消して入れ直すと、
> 注文時刻が新しくなり、お客さまには何の落ち度もないのに 10% が乗ります。
> そこで明細ごとに割増の対象から外せるようにしました。
> **注文時刻そのものは書き換えません。**「いつ厨房に入ったか」は提供時間の集計にも使う
> 事実の記録なので、事実は残し、判断（割増を取るか）だけを別の項目として持たせています。

### テストが 309 件すべて通っても、起動できないことがある

> 設定項目を増やしたとき、テストは全件通ったのに実際のデータベースでは起動しませんでした。
> Hibernate の `ddl-auto: update` は、**すでに行が入っているテーブルに NOT NULL の列を足せません**。
> 既存の行に何を入れるか決められないからです。
> テストは毎回まっさらな DB を作るため「無いテーブルを作る」経路しか通らず、
> この失敗は原理的に検出できませんでした。
> 以後、スキーマを変えたら必ず実データの入った DB で 1 回起動して確かめています。

### 「動くはず」で終わらせず、動かない理由を切り分ける

> スマホから開けない問題に半日かかりました。ping は通るのに 8080 番だけ届かない、
> という切り分けにくい症状で、原因は Windows ファイアウォールに残っていた
> Java への「拒否」ルールでした。**ファイアウォールは拒否が許可より常に強い**ため、
> 正しく許可を作っても効きません。ICMP はプログラムと無関係なので素通りし、
> Java が待つポートだけが落ちる、という現象になっていました。
> 以後、同じ回り道をしないよう Tomcat のアクセスログを有効にして、
> 「サーバまで届いているか」を一目で二分できるようにしています。

### 権限を下げるだけでは足りない（非 root コンテナ）

> Docker で非 root ユーザーに切り替えて動かす構成にしたところ、ビルドが必ず失敗しました。
> `WORKDIR /app` は root が作るので、そのあと一般ユーザーに切り替えてから
> `mkdir /app/data` を書いていたのが原因です。
> 仮にビルドが通っても、今度は起動できません。
> データベースのファイルも画像の保存先も作れないからです。
> **「権限を下げる」と「下げた先に必要な権限を渡す」はセットで一組**でした。
> ローカルは自分のユーザーで動かすので、この問題は原理的に再現しません。

### 例外が出ないバグがいちばん怖い

> 公開後、デモの厨房ボードが空になりました。例外もエラーも出ていません。
> ログを時刻順に読んで、**注文を作る処理が、卓とメニューを作る処理より先に走っていた**と分かりました。
> Spring は起動時処理が複数あるとき実行順を保証せず、
> 順序を書いていなければクラスパスを走査した順で決まります。環境が変われば変わる値です。
> 実際、同じコードがローカルでは正しい順、コンテナでは逆順で走りました。
>
> 厄介なのは、逆順でも**コードとしては正常に動く**ことです。
> 「対象が見つからなかったので 0 件作った」で終わり、起動もするし画面も出る。ただ中身が無い。
> 順序に意味があるなら明示する、とテストで固定しました。

### 手元では速いのに、公開すると重い

> 「もっさりする」と言われたとき、推測せずに測りました。
>
> | | 手元 | 公開先 |
> |---|---|---|
> | 疎通確認のみ | 8ms | 157ms |
> | メニュー画面 | 57ms | 1063ms |
>
> 通信分（150ms）を引くと、同じコードの描画が手元 57ms に対し公開先は約 910ms。
> 主因は無料枠の CPU で、これはコードでは直せません。
>
> ただ、測ったついでに直せるものが見つかりました。
> CSS に `Cache-Control: no-store` が付いていたのです。
> Spring Security が全レスポンスに付ける既定のヘッダで、HTML には正しいのですが、
> **静的ファイルにも乗るため、画面を移動するたびに CSS も JS も取り直していました。**
> 往復 8ms のローカルでは代償がゼロに見えるので、まったく気づけませんでした。
>
> 直すときも、長くキャッシュさせるだけでは
> 「CSS を直しても戻ってきた人の画面が変わらない」という別の問題が生まれます。
> 内容から作ったハッシュをファイル名に混ぜて、両立させました。

### 見えている不具合の裏に、別の原因があることがある

> メニューのタブが上に固定されない問題で、最初はヘッダーの高さが原因だと考えて直しました。
> それでも直らず、本当の原因は `position: sticky` の性質でした。
> **sticky は親要素の箱の中でしか貼り付きません。**
> タブを包む要素がタブと同じ高さしかなく、貼り付く余地が 0 だったのです。
> 症状が同じでも原因は別、という良い例でした。

### ログを埋める警告を放置しない

> `AsyncContext` の警告がログを埋めていました。
> 画面を閉じる・タブを切り替える、といったごく普通の操作で
> リアルタイム通信の接続は切れます。その切れた接続へ書き込もうとしていたのが原因でした。
> 実害は「ログが読めなくなる」ことですが、それは**本当のエラーを見逃す**という意味です。
> 接続ごとに生存フラグを持たせ、送る前に確認するようにしました。

## 5. 面接で聞かれたら

**「いちばん難しかったところは？」**

> 金額です。1 円でも多く請求すれば信用を失い、少なければ店が損をします。
> しかも間違いはその場では誰も気づかず、数日後にレジ締めが合わないという形で出てきます。
> だから計算は 1 箇所（`TableSession.recalculate`）にまとめ、
> 単価・税率は注文時点の値をコピーして保存し、
> あとから設定を変えても過去の伝票が動かないようにしました。

**「テストは何を書きましたか？」**

> 309 件のうち、いちばん厚いのは金額の計算です。
> 切り捨ての向き（お客さまに有利に）、キャンセルした注文の扱い、
> 同じ品を 1 回で頼んでも 2 回に分けても金額が変わらないこと、などを固定しています。
> 最後のものは、注文ごとに切り捨てると「分けて頼んだほうが安い」抜け道ができるためです。

**「1 人で作ったんですか？」**

> はい。ただし業務ルールは店主に確認しています。
