# 仕様書 — 米粉と鉄板 モバイルオーダー

最終更新: 2026-08-16

---

## 1. 何のためのシステムか

学芸大学の鉄板料理居酒屋「米粉と鉄板」で、**卓の QR からスマホで注文し、退店時にまとめて会計する**ためのシステム。

解決したい課題:

| 課題 | このシステムでの解決 |
|---|---|
| ピーク時に注文を取りに行けない | お客さんが自分のタイミングで注文できる |
| 口頭注文の聞き間違い・伝え漏れ | 注文が文字で厨房に届く。たこ焼きの味の組み合わせも取りこぼさない |
| 「いまいくら？」に答えられない | お客さんがいつでも伝票を確認できる |
| 会計の計算ミス | テーブルチャージ・深夜料金・消費税を自動計算 |
| 品切れの伝達が遅れる | 厨房のワンタップでお客さんの画面から消える |
| 何が売れているか分からない | 商品別ランキングと日次売上 |

**やらないこと**: オンライン決済（会計はレジ）、テイクアウト、会員機能、曜日別営業時間。

## 2. 登場人物と業務フロー

```
 お客さん            システム              厨房            ホール
 ─────────          ─────────            ─────────       ─────────
 卓のQRを読む   →   卓を特定
 人数を選ぶ     →   伝票を開く(OPEN)                  →  在席一覧に出る
 商品を選ぶ     →   カート（セッション）
 注文する       →   ① 受付可否チェック
                    ② 価格・品切れ再検証
                    ③ 注文番号を採番
                    ④ 伝票に注文を追加
                    ⑤ 伝票の金額を再計算
                    ⑥ SSE で通知          →  ボードに出る  →  金額が更新される
 伝票を見る     ←   現在のご請求額
                                             「調理開始」
                                             「提供待ち」
                                             「提供済み」  →  未提供が消える
 追加注文する   →   同じ伝票に積み上げ
 退店           ←                                          「お会計」
                    伝票を締める(CLOSED)                    → 売上に計上
```

### 注文の状態遷移

```
   RECEIVED ──→ COOKING ──→ READY ──→ COMPLETED
   （受付）      （調理中）   （提供待ち） （提供済み）
      │             │          │
      └─────────────┴──────────┴──→ CANCELED
                                ↑
                    READY → COOKING の巻き戻しも可（焼き直し）
```

- 許可されている遷移は `OrderStatus.allowedNext()` が唯一の定義。
  画面のボタンもサーバ側のチェックも、**両方これを見る**。
- お客さん自身のキャンセルは `RECEIVED` のときだけ（`Order.isCustomerCancelable()`）。
- **キャンセルされた注文は伝票の請求から外れる。**

### 伝票の状態遷移

```
   OPEN ──「お会計」──→ CLOSED
     ↑                     │
     └──「会計取消」────────┘
```

- `OPEN` の間だけ追加注文できる。
- 売上に数えるのは `CLOSED` の伝票だけ。
- 誤会計は `reopen()` で戻せる（レジ締め前のリカバリ用）。

## 3. データモデル

```
DiningTable（卓・QR固定）
     │
     └──< TableSession（伝票＝1回の来店）
                │
                └──< Order（注文）
                          │
                          └──< OrderLine ──< OrderLineOption

Category 1 ──< MenuItem 1 ──< OptionGroup 1 ──< OptionChoice
                   └── allergens: Set<Allergen>

DailyCounter   … 営業日ごとの注文番号採番（1日1行）
ShopSetting    … 店舗設定（常に1行、id=1）
StaffUser      … スタッフアカウント
```

### 主なテーブル

| テーブル | 役割 | 注意点 |
|---|---|---|
| `dining_table` | 卓 | `access_token` が QR に入る。連番 ID は URL に出さない |
| `table_session` | 伝票（来店） | 金額計算はこのエンティティに集約 |
| `orders` | 注文 | `ORDER` は SQL 予約語なので複数形。`session_id` 必須 |
| `order_line` / `order_line_option` | 明細 | 商品名・価格をスナップショットで持つ |
| `category` / `menu_item` | メニュー | 価格は税込 `int` |
| `menu_item_allergen` | アレルゲン（`@ElementCollection`） | EAGER。**未登録＝「未確認」として扱う** |
| `option_group` / `option_choice` | 味・サイズ・トッピング | `min_select` / `max_select` で入力形式が決まる |
| `daily_counter` | 注文番号カウンタ | 行ロックで採番。`Persistable` で必ず INSERT |
| `shop_setting` | 店舗設定 | 単一行（id=1） |
| `staff_user` | スタッフ | パスワードは BCrypt ハッシュのみ |

### 一意制約・インデックス

- `orders (business_date, order_number)` に UNIQUE — 同じ日に同じ番号ができないことを DB でも保証
- `dining_table.access_token` に UNIQUE
- `orders.status` / `orders.business_date` / `table_session.status` にインデックス

## 4. 業務ルール（重要な決めごと）

### 4.1 金額と税

- **すべて `int`（円）で扱う。** `double` は誤差が出るため禁止。
- 価格は**税込**で保持（日本の総額表示義務）。
- 税額は逆算：`税額 = 税込金額 × 税率 ÷ (100 + 税率)`（1 円未満切り捨て）。
  実装は `TaxCalculator.includedTax()` の 1 箇所だけ。
- **税率 10%。** 酒類を扱うため軽減税率（8%）の対象外。
- 注文には**注文時点の税率と価格を保存**する。あとで値上げしても過去の伝票は変わらない。

> ⚠️ **公式サイトのドリンクページには「表示価格は税抜きです」と明記されています。**
> 現在の投入データはサイト掲載の価格をそのまま入れているため、
> 営業に使う前に税込へ直すか、運用ルールを決めてください。

### 4.2 伝票の計算（`TableSession.recalculate`）

```
 小計            = キャンセル以外の注文の合計（税込）
 テーブルチャージ = tableChargePerGuest × guestCount

 深夜料金の対象額 = Σ（深夜帯に出した注文の合計）
                  ＋ 深夜帯に着席していれば テーブルチャージ
 深夜料金        = 対象額 × lateNightSurchargePercent / 100        ※切り捨て
 ─────────────────────────────────────────────
 ご請求額        = 小計 + テーブルチャージ + 深夜料金
 内消費税        = includedTax(ご請求額, taxRatePercent)
```

#### 深夜料金は「注文時刻」で決まる（会計時刻ではない）

同じ伝票の中で、通常料金の注文と深夜料金の注文が**混在します**。

```
 20:00 着席 4名   チャージ ¥450 × 4 = ¥1,800   → 着席が 20:00 なので対象外
 22:00 注文 ¥5,000                            → 通常料金
 23:30 注文 ¥3,000                            → 深夜料金の対象
 24:00 会計

 対象額   = ¥3,000
 深夜料金 = ¥3,000 × 10% = ¥300
 ご請求   = 5,000 + 3,000 + 1,800 + 300 = ¥10,100
```

- **注文** … `Order.createdAt`（注文時刻）で判定
- **テーブルチャージ** … `TableSession.openedAt`（着席時刻）で判定。注文ではないため

#### 打ち直し事故と、その救済（`Order.lateNightExempt`）

注文時刻で決めることの副作用として、**やり直すと時刻も新しくなる**問題がある。

```
 22:55  お客さまが注文        → 通常料金のはず
 23:05  スタッフが誤って取り消し
 23:06  お客さまが入れ直す    → 注文時刻が 23:06 になり 10% が乗る
```

お客さまは同じ品を同じ時間に頼んだだけなのに、**店側のミスで 10% 高くなる**。
注文はお客さまのスマホからしか作れないので、取り消したら入れ直してもらうしかなく、
この経路は必ず通る。

そこで**明細ごとに深夜料金の対象から外せる**ようにしている。
ホールの会計画面（`/hall/bills/{id}`）の各注文にボタンがあり、何度でも切り替えられる。

> **注文時刻そのものは書き換えない。**
> `createdAt` は「いつ厨房に入ったか」の記録でもあり提供時間の集計にも使う。
> 人が書き換えられるようにすると会計の証跡が信用できなくなる。
> **事実（何時の注文か）は残し、判断（割増を取るか）だけを別の項目で持つ。**

免除には 2 段階ある。混同しないこと。

| | 対象 | 使う場面 |
|---|---|---|
| `Order.lateNightExempt` | その注文だけ | 打ち直しの救済。会計前にいつでも切り替え可 |
| `TableSession.lateNightWaived` | 伝票全体（チャージ含む） | 会計時にまとめて免除。常連さんへのサービスなど |

判定役は `LateNightPolicy`（関数型インタフェース）として渡す。
真偽値を 1 つ渡す形だと「伝票全体に一律」しか表現できず、注文ごとの区別ができない。
スタッフによる免除は `LateNightPolicy.NONE` として表す。

**切り捨ては対象額を合計してから 1 回だけ**行う。注文ごとに割増して足すと、
切り捨てが件数ぶん効いて「分けて頼んだほうが安い」という抜け道ができる
（`splittingOrdersDoesNotChangeTheSurcharge` がこれを固定している）。

> **2026-08-18 まで会計時刻で伝票全体を判定していた。** 実店舗の運用と違っており、
> 22:00 に注文を終えて 23:00 過ぎまで話し込んだだけで全額に割増がかかり、
> 逆に 23:30 に注文して 5:00 過ぎに帰れば割増ゼロになっていた。

- **この計算はこの 1 箇所だけ。** 画面は getter を読むだけにする。
- 単価・割増率・税率は**来店時点の設定をコピー**して伝票に保存する。
  設定を変えても、すでに開いている伝票の金額は変わらない。

**設定変更が開いている伝票に効くか、効かないか**（間違えると金額トラブルになる）

| 設定 | 開いている伝票への影響 | 理由 |
|---|---|---|
| `taxRatePercent` | 効かない | 着席時に伝票へコピー |
| `tableChargePerGuest` | 効かない | 同上 |
| `lateNightSurchargePercent` | 効かない（**ただし 0 にすると外れる**） | 率はコピー済みだが、0 は `isLateNight` が false を返す |
| `lateNightStartTime` | **即座に効く** | コピーされず、毎回 `isLateNight` で判定し直す |
| `lateNightEndTime` | **即座に効く** | 同上 |

`TableService.applyCurrentAmounts()` が伝票を読むたびに、
そのときの店舗設定を判定役（`setting::isLateNight`）として渡して再計算するため、
**表示しただけでも計算し直される**。
営業中に深夜料金の時刻を縮めると、その瞬間に開いている全伝票から割増が消える。

ただし**スタッフが免除した伝票（`lateNightWaived = true`）は、
どんな設定になっても割増が復活しない**。
人の判断を、あとからの再計算で上書きしないため。

**時計が進んだだけでは金額は変わらない。** 深夜料金は注文時刻で決まるので、
22:00 で注文を終えたお客さまが 23:00 を過ぎるまで話し込んでも請求額は 1 円も動かない。
増えるのは **23:00 を過ぎてから追加注文したとき**だけ。

とはいえ「その注文にだけ割増がかかる」ことは頼む前に知らせる必要があるので、
お客さま伝票の下部に「23:00〜5:00 のご注文には深夜料金 10% を頂戴いたします」を
**割増がかかっていないうちから常に**出している（`customer/bill.html`）。
「お会計には」と書くと早い時間の注文にもかかると誤解されるので、必ず「ご注文には」と書く。

### 4.1.1 メニュー画面のタブ（大カテゴリ）

カテゴリは 14 個ある。そのまま横一列のタブにすると端まで探しに行けないので、
`Category.groupName`（大カテゴリ）が同じものを 1 つのタブにまとめる。

| タブ | 中に入るカテゴリ |
|---|---|
| お好み焼き | 広島風お好み焼き |
| たこ焼き | 選べる米粉たこ焼き |
| 鉄板料理 | 鉄板おつまみ ／ 鉄板麺 ／ 数量限定鉄板焼き |
| 一品料理 | 一品料理 ／ 甘味 |
| ドリンク | ビール・サワー 〜 日本酒・ワイン（7 カテゴリ） |

- **`groupName` が空なら、そのカテゴリ名がそのままタブになる。**
  新しいカテゴリを足して設定を忘れても、メニューから消えたりしない。
- タブの並びは、そのタブに入っているカテゴリのいちばん小さい `sortOrder` で決まる。
- 管理画面（カテゴリ）から自由に変えられる。初期値は `DataSeeder` が `sortOrder` から割り当てる。

**操作は 3 通り**（マクドナルドのモバイル注文と同じ形）。

1. タブを押す
2. **左右にスワイプ**する
3. タブに焦点がある状態で ← → キー

スワイプは JavaScript で指を追いかけているのではなく、
**横スクロール ＋ `scroll-snap-type: x mandatory`** に任せている。
自前で実装すると慣性やはじきが不自然になるが、標準の仕組みなら OS 本来の動きが出る。
JS がやるのは「いまどの面か」をタブに反映することと、タブが押されたら寄せることだけ。

> **面の高さは JS で詰めている。** 横に並べた箱の高さは「いちばん高い面」に揃うため、
> 何もしないとお好み焼き（911px）を見ているときに、
> ドリンク（9131px）に引きずられて下に 8000px の空白が続く。
> 表示中の面の高さを箱に設定して回避している（`menu.html` の `fitHeight`）。

> **「いまどの面か」の判定に `IntersectionObserver` を使わない理由。**
> 最初はそれで書いたが、横スクロールする箱を `root` にすると
> 環境によってはコールバックが一度も飛ばない。
> `scrollLeft ÷ 面の幅` を四捨五入すれば済むものを、凝った仕組みに任せる必要はない。

### 4.2.0 消費税率が変わったときに何ができて、何ができないか

（2026-08-18 調査。「テイクアウトの税率が 8% から変わるかもしれない」を受けて）

**税率そのものの変更は 1 分で終わる。**
管理画面 → 店舗設定 → 消費税率 を書き換えて保存するだけ。
`taxRatePercent` は `int`（0〜100）なので **1% でも 0% でも入る**。
`TaxCalculator.includedTax` は `金額 × 率 ÷ (100 + 率)` なので率を選ばない。
**過去の伝票・注文は税率をコピーして持っている**（`Order.taxRatePercent` /
`TableSession.taxRatePercent`）ので、あとから設定を変えても遡って書き換わらない。

> ⚠ **税率を下げても、お客さまの支払額は 1 円も下がらない。**
> 価格は税込（内税）で持っているため、率を変えると
> **レシートに出る「内消費税」の内訳だけが変わる**。
> お客さまに還元するなら、**商品価格そのものを下げる作業が別に必要**。
> 逆に価格を据え置けば、下がったぶんは店の取り分になる。どちらにするかは経営判断。

**できないこと（対応するなら実装が要る）**

| やりたいこと | いまの状態 | 必要な作業 |
|---|---|---|
| イートイン 10% と テイクアウト 8%(→1%) を**同時に**持つ | 店に税率が 1 つだけ | `ShopSetting` に持ち帰り用税率を足し、注文時に選ぶ。器（`Order.taxRatePercent`）は既にある |
| 商品ごとに税率を変える（**酒類は持ち帰りでも軽減税率の対象外**） | `OrderLine` に税率が無い。`MenuItem` に酒類フラグも無い | `MenuItem` に税区分、`OrderLine` に税率を追加。**ここが一番大きい** |
| 8.5% のような小数の税率 | `int` なので不可 | 率を「千分率」で持つなどの変更が必要。実際に必要になる可能性は低い |

なお現在このシステムは**卓番QR（イートイン専用）**で、テイクアウトの注文導線そのものが無い。
テイクアウトを扱うなら、税率より先にその導線を作るところから。

### 4.2.1 深夜料金の境界は他の設定に一切影響されない

`isLateNight` が見るのは `lateNightStartTime` / `lateNightEndTime` / `lateNightSurchargePercent`
の 3 つだけ。**開店時刻・ラストオーダー・閉店・24 時間受付・営業日の切り替え時刻を
どう動かしても、深夜料金の境界は 1 秒も動かない。**

「時刻を円として扱い、起点から何秒進んだかで比較する」という説明は、
起点が 1 つしか無いように読めてしまうが、**起点は範囲ごとに別**である。
営業時間の起点は `openTime`、深夜料金の起点は `lateNightStartTime`。

`ShopSettingTest$LateNightRange` の
`independentFromOpenTime` / `independentFromOtherHours` / `boundaryIsExactToTheSecond`
がこれを固定している（開店時刻を 0:00〜22:59 まで振っても 23:00 の境界が動かないこと、
22:59:59 は通常料金で 23:00:00 ちょうどから深夜であること）。
- 深夜料金の判定は `ShopSetting.isLateNight()`。
  `lateNightStartTime`（既定 23:00）〜 `lateNightEndTime`（既定 5:00）の範囲。
  **開始ちょうどは深夜、終了ちょうどはもう深夜ではない**（半開区間）。
  単純に `t >= 23:00` と書くと深夜 1:00 が対象外になるため、範囲として持っている。
- 終了時刻は **2026-08-18 に追加**。それ以前は `businessDayCutoverHour` を
  深夜の終わりとして流用していたが、「売上をどの日に数えるか」と
  「深夜料金の範囲」は本来別物で、集計基準を直すと料金まで動く連動が事故のもとだった。
  いまは互いに独立している。
- ホール画面でスタッフが深夜料金を**外せる**（サービス対応のため）。

### 4.3 注文番号

- 営業日ごとに `ShopSetting.orderNumberStart`（既定 101）から連番。
- 採番は `DailyCounter` を **悲観ロック（`SELECT ... FOR UPDATE`）** して行う。
- 採番だけ `Propagation.REQUIRES_NEW` の別トランザクション。理由は 2 つ:
  1. ロックを握る時間を最短にして同時注文を詰まらせない
  2. 注文本体の保存に失敗しても採番の状態が壊れない
- `DailyCounter` は `Persistable` を実装し、新規なら必ず INSERT になるようにしている。
  そうしないと「初回同時注文でカウンタが巻き戻る」競合が起きる。
- **番号は飛んでもよい。** 番号を再利用するほうが事故になる。

### 4.4 営業日

- 暦の日付ではなく「営業日」で集計する。
- `ShopSetting.businessDayCutoverHour`（既定 5 時）より前の注文は**前日の営業日**として扱う。
- 深夜 1 時の注文も「その日の営業」として売上に入る。
- **効くのは売上の集計と注文番号だけ。** 深夜料金の範囲とは無関係
  （4.2 参照。2026-08-18 に切り離した）。

### 4.5 受付可否

`ShopSetting.isOrderAcceptable(now)` が唯一の判定。

1. `acceptingOrders = true`（店長が手動で止めていない）
2. 営業時間内（**日をまたぐ営業に対応**）。ただし `alwaysOpen = true` なら時刻では止めない
3. 伝票が `OPEN`（会計済みの卓からは注文できない）

**時刻はすべて 0:00〜23:59 の任意の値**を設定画面から入れられる（選択肢は固定されていない）。

`alwaysOpen`（24 時間受付）は **2026-08-18 に追加**。3 つの用途がある。

- **動作確認**… 営業時間外は人数選択すら押せないので、確認のたびに営業時間を
  いじって戻し忘れる事故が起きていた
- **急な営業時間の変更**… 「今夜だけ朝までやる」に、時刻を計算し直さず対応できる
- **24 時間営業の店**… そもそも開店・閉店の区切りが無い

`acceptingOrders`（今すぐ止める非常ブレーキ）とは**独立**していて、
24 時間受付でも手動停止はいつでも効く。
営業時間の値は消さずに残るので、OFF に戻せばそのまま元の営業時間に戻る。

### 4.5.1 日をまたぐ時刻範囲の扱い

営業時間（17:30〜翌 1:30）と深夜料金（23:00〜翌 5:00）は、
どちらも「**日をまたぐかもしれない時刻の範囲**」という同じ形をしている。
そこで判定を 1 つの考え方に統一している（`ShopSetting` の private メソッド）。

```
secondsFrom(from, t) = floorMod(t - from, 24時間)    // from から時計回りに何秒進んだか
isBetween(t, from, to)            = secondsFrom(from, t) <= secondsFrom(from, to)   // 終端を含む
isBetweenExcludingEnd(t, from, to) = secondsFrom(from, t) <  secondsFrom(from, to)  // 終端を含まない
```

時刻を直線ではなく**24 時間で一周する円**として扱うと、
「日をまたぐか」の場合分けが要らなくなる。
`Math.floorMod` を使うのは、Java の `%` が負の余りを返す（`-3 % 24 == -3`）ため。

この形にしてあるので、営業時間を 24 時間受付に変えても
**深夜料金の実装は 1 行も変わらない**。

### 4.6 カートの再検証（重要）

カートはブラウザのセッションに置かれるため、入れてから注文するまでの間に
値上げ・品切れ・商品削除が起きうる。

`OrderService.placeOrder()` は保存前に必ず `CartService.refresh()` を通し、
1 つでも変化があれば**注文を通さず**、更新後のカートと変更内容を見せて再確認してもらう。

> セッションの値をそのまま信じて会計すると、実際の売価と違う金額で受け付けてしまう。
> ここは金銭事故に直結するので、迷ったら「通さない」側に倒す。

### 4.7 残数（在庫）— 2026-08-17 追加

- `MenuItem.stockRemaining` が **null なら「在庫を管理しない」**（ドリンク等）。
  数字を入れた品だけが残数管理の対象（数量限定鉄板焼きなどのオプトイン方式）。
- 減らすのは**条件付き UPDATE 1 文**（`MenuItemRepository.tryDecrementStock`）。
  「読んで、引いて、書き戻す」は競合状態になるため禁止。
  残り 1 皿に 2 卓が同時注文しても、片方だけが成功することを DB が保証する。
- 減算は**注文番号の採番より前**に行う（在庫切れで断るたびに番号が飛ぶのを避ける）。
  複数商品の注文で途中の品が在庫不足なら、トランザクションのロールバックで
  先に引いた分も自動で戻る。
- **キャンセルで残数は戻る**。どのキャンセル経路（店側・客側・汎用の状態変更）でも戻し、
  かつ「初めてキャンセルになったときだけ」戻す（二重リストア防止）。
- 残数 0 は画面上「売り切れ」（手動の品切れフラグと同じ見た目）。
  お客さま画面には「残り N 点」バッジを表示（限定感は注文の後押しにもなる）。
- 残数の設定・解除は 厨房画面 → 品切れ・残数管理。**日次の自動リセットはしない**
  （仕込み数は日によって違うので、開店前にスタッフが入れる運用）。

### 4.8 アレルゲン

- **アレルゲンが 1 件も登録されていない商品は「未確認」として扱う。**
  画面には「アレルギーは店舗へお尋ねください」と出し、「小麦不使用」バッジは出さない。
- 「調べた結果ふくまれていない」のか「まだ登録していないだけ」なのかを
  お客さんが区別できないと、誤った安心を与えてしまうため。
- 初期投入データは**意図的に未登録**。店舗が原材料表示を確認して登録する運用。

### 4.8 売上の計上

- 伝票（`TableSession`）が `CLOSED` になった時点で確定。
- 商品別ランキングは `OrderStatus.COMPLETED` の明細から集計（`SalesReportService`）。
  **伝票ベースの総額とはテーブルチャージ・深夜料金のぶんズレる**ので、
  画面上でどちらの数字か分かるようにしている。

## 6. 設計判断とその理由

| 判断 | 理由 | 代替案と却下理由 |
|---|---|---|
| 卓 QR は固定、伝票は来店ごと | QR を貼り替えずに済み、前の客の伝票も見えない | 伝票ごとに QR → 毎回印刷が必要で運用が回らない |
| 伝票の金額計算を 1 クラスに集約 | 会計は間違えると実害。散らばると必ずズレる | 画面ごとに計算 → 表示と請求が食い違う |
| 設定を伝票にコピー | 営業中に設定を変えても既存の伝票が壊れない | マスタ参照 → 会計の証跡として成立しない |
| Thymeleaf（サーバサイド描画） | 画面数が少なく SEO も不要。学習コストが最小 | React/Vue → ビルド構成が増える |
| カートをセッションに置く | ログイン不要の匿名注文で最も単純 | DB に持つ → 匿名ユーザーのゴミデータが溜まる |
| SSE（WebSocket ではなく） | サーバ→ブラウザの一方向で足りる | WebSocket → 双方向は不要なのに実装が重い |
| 明細に価格をスナップショット | 値上げしても過去の伝票が変わらない | マスタ参照 → 会計の証跡にならない |
| 採番専用テーブル + 悲観ロック | 同時注文で番号が重複しない | MAX+1 → 競合状態で重複する |
| `open-in-view: false` | 画面描画中に DB 接続を握らない | true（既定）→ 接続枯渇の温床 |
| 金額は `int` | 円に小数はない。誤差ゼロ | `double` → 金額がズレる |
| QR に UUID トークン | 番号を変えて他卓の伝票を覗けない | 連番 ID → 総当たりで覗ける |
| Lombok を使わない | getter/setter が見えるほうが学習になる | Lombok → 生成コードが見えず混乱する |
| CSS フレームワーク不使用 | 和モダンな見た目を細部まで作り込むため | Bootstrap → どこかで見た画面になる |
| 外部フォント・CDN 不使用 | 店内 Wi-Fi にネットが無くても崩れない | Google Fonts → オフラインで文字化け |

## 7. セキュリティ上の考慮

| 脅威 | 対策 |
|---|---|
| 他卓の伝票を覗かれる | 連番 ID ではなく UUID の `accessToken` で参照（ケイパビリティ URL） |
| CSRF | Spring Security 既定で有効。フォームは `th:action` で自動的にトークンが入る |
| 価格の改ざん | 送信された価格は一切信用せず、必ず DB の現在価格で再計算 |
| 存在しない選択肢の混入 | この商品に属さない選択肢 ID が来たら拒否（`CartService`） |
| 品切れ商品の注文 | カート追加時と注文確定時の 2 回チェック |
| 会計済みの卓からの注文 | `TableSession.isOrderable()` で拒否 |
| パスワード漏洩 | BCrypt ハッシュのみ保存。初期パスワードは自動生成しログに 1 回だけ表示 |
| ユーザー名の存在推測 | 認証失敗メッセージを統一、`hideUserNotFoundExceptions` を有効化 |
| ディレクトリトラバーサル | アップロード名は UUID で作り直し、保存先が上位に出ないか検証 |
| 不正なファイルのアップロード | 拡張子と Content-Type の両方を許可リストで検証。5MB 上限 |
| セッションのメモリ枯渇 | カートに行数・個数の上限（30 種類 / 1 行 20 個） |
| 状態遷移の飛ばし | 画面のボタンだけでなくサーバ側でも `allowedNext()` を検証 |

### 残っているリスク（承知のうえ）

- **同じ店内の別の人**が卓の QR を撮れば、その卓の伝票を見られる。
  店内に貼る性質上これは防げないため、店舗運用で許容する。
- **年齢確認ができない。** 酒類の提供時に店頭で必ず確認する運用が前提。
- SSE の接続はインメモリ保持のため、**アプリを複数台に負荷分散すると通知が届かない**。
  1 台運用が前提。
- 同じ卓に同時に 2 人が QR を読むと、理論上は伝票が 2 つできうる。
  DB の部分一意制約が製品依存になるため採用せず、ホール画面から統合する運用でカバー。
- レート制限を入れていない。公開インターネットに出す場合は要検討。

## 8. 今後の課題

優先度順。

1. **価格の税抜／税込の確定**
   ドリンクは公式サイトに「税抜」と明記されている。投入データはサイト表記のまま。
   **営業に使う前に必ず整理すること。**
2. **アレルゲンの登録**
   全商品が未登録。店舗で原材料を確認して入れる。
3. **DB マイグレーション（Flyway）の導入**
   いまは dev が `ddl-auto: update`、prod が `validate`。
   本番でスキーマを変えるには手動 DDL が必要な状態。
   なお `ddl-auto: update` は**既存データのあるテーブルに NOT NULL 列を足せない**
   （既存の行に何を入れるか決められないため）。
   2026-08-18 に実際に起動できなくなった。当面の対処は
   `@Column(columnDefinition = "... not null default ...")` で既定値を書くこと。
   **この失敗はテストでは絶対に再現しない**（テストは毎回まっさらな DB を作るので、
   「無いテーブルを作る」経路しか通らない）。実データの入った DB で一度起動して確かめること。
4. **曜日別の営業時間**
   土日は 16:00 開店だが、設定は 1 組しか持てない。
   当面は「24 時間受付」を ON にするか、その日だけ開店時刻を書き換えて運用する。
5. **レシート印刷**
   いまは画面表示のみ。ESC/POS 対応のサーマルプリンタ連携があると実用度が上がる。
6. **割り勘・部分会計**
   伝票を分けて会計する機能はない。
7. **画像のリサイズ**
   アップロードした画像をそのまま配信している。
8. ~~**バックアップ**~~ → **実装済み（2026-08-17）**
   定時（4:30）・アプリ終了時・手動の 3 タイミングで DB と画像を退避。
   世代管理と 2次コピー先の設定あり。復元手順は `docs/バックアップと復元.md`。
   **残タスク**: `app.backup.extra-copy-dir` に USB / OneDrive のパスを実際に設定すること
   （未設定だと同じディスク内のコピーであり、ディスク故障には無力）。
9. **監視**
   死活監視・エラー通知の仕組みは無し。営業中に落ちても気づけるのは画面が止まったとき。
