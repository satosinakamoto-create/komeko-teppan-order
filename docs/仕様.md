# 仕様書 — 米粉と鉄板 モバイルオーダー

最終更新: 2026-08-16

---

## 1. 何のためのシステムか

米粉と鉄板を使ったテイクアウト店で、**レジ前の行列と口頭注文の聞き間違いをなくす**ためのシステム。

解決したい課題:

| 課題 | このシステムでの解決 |
|---|---|
| ピーク時にレジが詰まる | お客さんが並ばずにスマホから注文できる |
| 口頭注文の聞き間違い・伝え漏れ | 注文が文字で厨房に届く。オプションも取りこぼさない |
| 「あとどれくらい？」に答えられない | 待ち組数と待ち時間の目安を自動で表示 |
| 品切れの伝達が遅れる | 厨房のワンタップでお客さんの画面から消える |
| 何が売れているか分からない | 商品別ランキングと時間帯別売上 |

**やらないこと**: オンライン決済（会計は店頭）、イートイン、会員機能。

## 2. 登場人物と業務フロー

```
 お客さん            システム                厨房                サイネージ
 ─────────          ─────────              ─────────           ─────────
 QR を読む     →    メニュー表示
 商品を選ぶ    →    カート（セッション）
 注文する      →    ① 受付可否チェック
                    ② 価格・品切れ再検証
                    ③ 注文番号を採番
                    ④ 保存
                    ⑤ SSE で通知        →  ボードに出る    →  （まだ出ない）
 番号が出る    ←    控えページ
                                            「調理開始」    →  「調理中」に表示
                                            「焼き上がり」  →  「お呼び出し中」に表示 ＋ チャイム
 番号を見る    ←    5秒ポーリングで更新
 受け取る・会計                             「受渡済」      →  表示から消える
```

### 状態遷移

```
   RECEIVED ──→ COOKING ──→ READY ──→ COMPLETED
      │             │          │
      └─────────────┴──────────┴──→ CANCELED
                                ↑
                    READY → COOKING の巻き戻しも可（焼き直し）
```

- 許可されている遷移は `OrderStatus.allowedNext()` が唯一の定義。
  画面のボタンもサーバ側のチェックも、**両方これを見る**。
- `COMPLETED` からはどこへも進めない（伝票クローズ）。
- お客さん自身のキャンセルは `RECEIVED` のときだけ（`Order.isCustomerCancelable()`）。

## 3. データモデル

```
Category 1 ──< MenuItem 1 ──< OptionGroup 1 ──< OptionChoice
                   │
                   └── allergens: Set<Allergen>   (menu_item_allergen)

Order 1 ──< OrderLine 1 ──< OrderLineOption
                                     ↑
                     すべて「注文時点のコピー」を保持する

DailyCounter   … 営業日ごとの採番（1日1行）
ShopSetting    … 店舗設定（常に1行、id=1）
StaffUser      … スタッフアカウント
```

### 主なテーブル

| テーブル | 役割 | 注意点 |
|---|---|---|
| `category` | メニューのカテゴリ | `visible=false` で客側から隠せる |
| `menu_item` | 商品 | 価格は税込 `int`。`sold_out` は品切れ |
| `menu_item_allergen` | アレルゲン（`@ElementCollection`） | EAGER。表示に必ず使うため |
| `option_group` / `option_choice` | サイズ・トッピング | `min_select` / `max_select` で入力形式が決まる |
| `orders` | 注文（伝票） | `ORDER` は SQL 予約語なので複数形 |
| `order_line` / `order_line_option` | 明細 | 商品名・価格をスナップショットで持つ |
| `daily_counter` | 注文番号カウンタ | 行ロックで採番。1日1行 |
| `shop_setting` | 店舗設定 | 単一行（id=1） |
| `staff_user` | スタッフ | パスワードは BCrypt ハッシュのみ |

### 一意制約・インデックス

- `orders (business_date, order_number)` に UNIQUE
  → 同じ日に同じ番号が 2 つできないことを **DB 側でも保証**する
- `orders.public_token` に UNIQUE
- `orders.status` / `orders.business_date` にインデックス（ボード表示・集計で毎回引くため）

## 4. 業務ルール（重要な決めごと）

### 4.1 金額と税

- **すべて `int`（円）で扱う。** `double` は誤差が出るため禁止。
- 価格は**税込**で保持（日本の総額表示義務）。
- 税額は逆算：`税額 = 税込金額 × 税率 ÷ (100 + 税率)`（1 円未満切り捨て）。
  実装は `TaxCalculator.includedTax()` の 1 箇所だけ。
- テイクアウトは**軽減税率 8%**。設定値 `ShopSetting.taxRatePercent`。
- 注文には**注文時点の税率と価格を保存**する。あとで値上げしても過去の伝票は変わらない。

### 4.2 注文番号

- 営業日ごとに `ShopSetting.orderNumberStart`（既定 101）から連番。
- 採番は `DailyCounter` を **悲観ロック（`SELECT ... FOR UPDATE`）** して行う。
- 採番だけ `Propagation.REQUIRES_NEW` の別トランザクションにしている。理由は 2 つ:
  1. ロックを握る時間を最短にして同時注文を詰まらせない
  2. 注文本体の保存に失敗しても採番の状態が壊れない
- **番号は飛んでもよい。** 番号を再利用して別のお客さんに同じ番号を渡すほうが事故になる。

### 4.3 営業日

- 暦の日付ではなく「営業日」で集計する。
- `ShopSetting.businessDayCutoverHour`（既定 5 時）より前の注文は**前日の営業日**として扱う。
- 深夜営業をしない店なら既定のままでよい。

### 4.4 受付可否

`ShopSetting.isOrderAcceptable(now)` が唯一の判定。以下すべてを満たすときのみ受付。

1. `acceptingOrders = true`（店長が手動で止めていない）
2. `openTime` を過ぎている
3. `lastOrderTime` を過ぎていない

### 4.5 カートの再検証（重要）

カートはブラウザのセッションに置かれるため、**入れてから注文するまでの間に**
値上げ・品切れ・商品削除が起きうる。

`OrderService.placeOrder()` は保存前に必ず `CartService.refresh()` を通し、
1 つでも変化があれば**注文を通さず**、更新後のカートと変更内容を見せて再確認してもらう。

> セッションの値をそのまま信じて会計すると、実際の売価と違う金額で受け付けてしまう。
> ここは金銭事故に直結するので、迷ったら「通さない」側に倒す。

### 4.6 待ち時間の目安

```
待ち時間 ＝ (自分より前に並ぶ注文の調理時間合計 ÷ 鉄板の同時焼成数)
          ＋ (自分の注文の調理時間 ÷ 鉄板の同時焼成数)
          −  すでに経過した時間
```

- 上限 120 分でクリップし、マイナスは「まもなく」と表示。
- 厳密な予測ではなく**体感に近い目安**が目的。少し長めに出すほうが満足度が上がる。
- `ShopSetting.griddleCapacity` が「鉄板で同時に焼ける数」。

### 4.7 売上の計上

- 売上に数えるのは **`COMPLETED`（受渡済）のみ**。
- 調理中・キャンセルは含めない。
- 定義は `SalesReportService.SALES_STATUS` の 1 箇所だけ。他で真似して書かない。

## 6. 設計判断とその理由

| 判断 | 理由 | 代替案と却下理由 |
|---|---|---|
| Thymeleaf（サーバサイド描画） | 画面数が少なく、SEO も不要。学習コストが最小 | React/Vue → ビルド構成が増え、初学者の学習対象が分散する |
| カートをセッションに置く | ログイン不要の匿名注文で最も単純 | DB に持つ → 匿名ユーザーのゴミデータが溜まる |
| SSE（WebSocket ではなく） | サーバ→ブラウザの一方向で足りる | WebSocket → 双方向は不要なのに実装が重い |
| 明細に価格をスナップショット | 値上げしても過去の伝票が変わらない | マスタ参照 → 会計の証跡として成立しない |
| 採番専用テーブル + 悲観ロック | 同時注文で番号が重複しない | MAX+1 → 競合状態で重複する |
| `open-in-view: false` | 画面描画中に DB 接続を握らない | true（既定）→ 接続枯渇の温床。本番で事故る |
| 金額は `int` | 円に小数はない。誤差ゼロ | `double` → 0.1 を表現できず金額がズレる |
| ID ではなく UUID トークンで注文参照 | 番号を変えて他人の注文を覗けない | 連番 ID → 総当たりで他人の注文が見える |
| Lombok を使わない | getter/setter が実際に見えるほうが学習になる | Lombok → 生成コードが見えず初学者が混乱する |
| CSS フレームワーク不使用 | 和モダンな見た目を細部まで作り込むため | Bootstrap → どこかで見た画面になる |
| 外部フォント・CDN 不使用 | 店内 Wi-Fi にネットが無くても崩れない | Google Fonts → オフラインで文字が化ける |

## 7. セキュリティ上の考慮

| 脅威 | 対策 |
|---|---|
| 他人の注文を覗かれる | 連番 ID ではなく UUID の `publicToken` で参照（ケイパビリティ URL） |
| CSRF | Spring Security 既定で有効。フォームは `th:action` で自動的にトークンが入る |
| 価格の改ざん | 送信された価格は一切信用せず、必ず DB の現在価格で再計算 |
| 存在しない選択肢の混入 | この商品に属さない選択肢 ID が来たら拒否（`CartService`） |
| 品切れ商品の注文 | カート追加時と注文確定時の 2 回チェック |
| パスワード漏洩 | BCrypt ハッシュのみ保存。ログにも出さない |
| ユーザー名の存在推測 | 認証失敗メッセージを統一、`hideUserNotFoundExceptions` を有効化 |
| ディレクトリトラバーサル | アップロード名は UUID で作り直し、保存先が上位に出ないか検証 |
| 不正なファイルのアップロード | 拡張子と Content-Type の両方を許可リストで検証。5MB 上限 |
| セッションのメモリ枯渇 | カートに行数・個数の上限（30 種類 / 1 行 20 個） |
| 状態遷移の飛ばし | 画面のボタンだけでなくサーバ側でも `allowedNext()` を検証 |

### 残っているリスク（承知のうえ）

- `/display` は認証なしで見られる。番号しか出ないが、店外から見える位置に置くなら要検討。
- SSE の接続はインメモリ保持のため、**アプリを複数台に負荷分散すると通知が届かない**。
  1 台運用が前提。分散する場合は Redis Pub/Sub などを挟む必要がある。
- レート制限を入れていない。公開インターネットに出す場合は、
  注文 API に IP 単位の制限（例: Bucket4j）を足すこと。

## 8. 今後の課題

優先度順。

1. **DB マイグレーション（Flyway）の導入**
   いまは dev が `ddl-auto: update`、prod が `validate`。
   本番でスキーマを変えるには手動 DDL が必要な状態。Flyway を入れて履歴管理する。
2. **注文の締め処理／日次レポート**
   営業終了時に未完了の注文を一括でクローズする画面がまだない。
3. **レシート印刷**
   いまは画面表示のみ。ESC/POS 対応のサーマルプリンタ連携があると実用度が上がる。
4. **画像のリサイズ**
   アップロードした画像をそのまま配信している。サムネイル生成を入れると通信量が減る。
5. **イートイン対応**
   卓番 QR と 10% 課税。`Order.taxRatePercent` を注文ごとに持たせてあるので拡張は可能。
6. **多言語対応**
   `messages.properties` の仕組みは設定済み（`spring.messages.basename`）だが未使用。
7. **監視・バックアップ**
   H2 のファイルを定期コピーする仕組み。営業データが飛ぶと痛い。
