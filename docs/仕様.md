# 仕様書 — 米粉と鉄板 モバイルオーダー

最終更新: 2026-08-16

---

## 1. 何のためのシステムか

学芸大学の鉄板料理居酒屋「米粉と鉄板」で、**卓の QR からスマホで注文し、退店時にまとめて会計する**ためのシステム。

解決したい課題:

| 課題 | このシステムでの解決 |
|---|---|
| ピーク時に注文を取りに行けない | お客さんが自分のタイミングで注文できる |
| 口頭注文の聞き間違い・伝え漏れ | 注文が文字で厨房に届く。たこ焼きの味の組み合わせも取りこぼさない |
| 「いまいくら？」に答えられない | お客さんがいつでも伝票を確認できる |
| 会計の計算ミス | テーブルチャージ・深夜料金・消費税を自動計算 |
| 品切れの伝達が遅れる | 厨房のワンタップでお客さんの画面から消える |
| 何が売れているか分からない | 商品別ランキングと日次売上 |

**やらないこと**: オンライン決済（会計はレジ）、テイクアウト、会員機能、曜日別営業時間。

## 2. 登場人物と業務フロー

```
 お客さん            システム              厨房            ホール
 ─────────          ─────────            ─────────       ─────────
 卓のQRを読む   →   卓を特定
 人数を選ぶ     →   伝票を開く(OPEN)                  →  在席一覧に出る
 商品を選ぶ     →   カート（セッション）
 注文する       →   ① 受付可否チェック
                    ② 価格・品切れ再検証
                    ③ 注文番号を採番
                    ④ 伝票に注文を追加
                    ⑤ 伝票の金額を再計算
                    ⑥ SSE で通知          →  ボードに出る  →  金額が更新される
 伝票を見る     ←   現在のご請求額
                                             「調理開始」
                                             「提供待ち」
                                             「提供済み」  →  未提供が消える
 追加注文する   →   同じ伝票に積み上げ
 退店           ←                                          「お会計」
                    伝票を締める(CLOSED)                    → 売上に計上
```

### 注文の状態遷移

```
   RECEIVED ──→ COOKING ──→ READY ──→ COMPLETED
   （受付）      （調理中）   （提供待ち） （提供済み）
      │             │          │
      └─────────────┴──────────┴──→ CANCELED
                                ↑
                    READY → COOKING の巻き戻しも可（焼き直し）
```

- 許可されている遷移は `OrderStatus.allowedNext()` が唯一の定義。
  画面のボタンもサーバ側のチェックも、**両方これを見る**。
- お客さん自身のキャンセルは `RECEIVED` のときだけ（`Order.isCustomerCancelable()`）。
- **キャンセルされた注文は伝票の請求から外れる。**

### 伝票の状態遷移

```
   OPEN ──「お会計」──→ CLOSED
     ↑                     │
     └──「会計取消」────────┘
```

- `OPEN` の間だけ追加注文できる。
- 売上に数えるのは `CLOSED` の伝票だけ。
- 誤会計は `reopen()` で戻せる（レジ締め前のリカバリ用）。

## 3. データモデル

```
DiningTable（卓・QR固定）
     │
     └──< TableSession（伝票＝1回の来店）
                │
                └──< Order（注文）
                          │
                          └──< OrderLine ──< OrderLineOption

Category 1 ──< MenuItem 1 ──< OptionGroup 1 ──< OptionChoice
                   └── allergens: Set<Allergen>

DailyCounter   … 営業日ごとの注文番号採番（1日1行）
ShopSetting    … 店舗設定（常に1行、id=1）
StaffUser      … スタッフアカウント
```

### 主なテーブル

| テーブル | 役割 | 注意点 |
|---|---|---|
| `dining_table` | 卓 | `access_token` が QR に入る。連番 ID は URL に出さない |
| `table_session` | 伝票（来店） | 金額計算はこのエンティティに集約 |
| `orders` | 注文 | `ORDER` は SQL 予約語なので複数形。`session_id` 必須 |
| `order_line` / `order_line_option` | 明細 | 商品名・価格をスナップショットで持つ |
| `category` / `menu_item` | メニュー | 価格は税込 `int` |
| `menu_item_allergen` | アレルゲン（`@ElementCollection`） | EAGER。**未登録＝「未確認」として扱う** |
| `option_group` / `option_choice` | 味・サイズ・トッピング | `min_select` / `max_select` で入力形式が決まる |
| `daily_counter` | 注文番号カウンタ | 行ロックで採番。`Persistable` で必ず INSERT |
| `shop_setting` | 店舗設定 | 単一行（id=1） |
| `staff_user` | スタッフ | パスワードは BCrypt ハッシュのみ |

### 一意制約・インデックス

- `orders (business_date, order_number)` に UNIQUE — 同じ日に同じ番号ができないことを DB でも保証
- `dining_table.access_token` に UNIQUE
- `orders.status` / `orders.business_date` / `table_session.status` にインデックス

## 4. 業務ルール（重要な決めごと）

### 4.1 金額と税

- **すべて `int`（円）で扱う。** `double` は誤差が出るため禁止。
- 価格は**税込**で保持（日本の総額表示義務）。
- 税額は逆算：`税額 = 税込金額 × 税率 ÷ (100 + 税率)`（1 円未満切り捨て）。
  実装は `TaxCalculator.includedTax()` の 1 箇所だけ。
- **税率 10%。** 酒類を扱うため軽減税率（8%）の対象外。
- 注文には**注文時点の税率と価格を保存**する。あとで値上げしても過去の伝票は変わらない。

> ⚠️ **公式サイトのドリンクページには「表示価格は税抜きです」と明記されています。**
> 現在の投入データはサイト掲載の価格をそのまま入れているため、
> 営業に使う前に税込へ直すか、運用ルールを決めてください。

### 4.2 伝票の計算（`TableSession.recalculate`）

```
 小計            = キャンセル以外の注文の合計（税込）
 テーブルチャージ = tableChargePerGuest × guestCount
 深夜料金        = (小計 + テーブルチャージ) × lateNightSurchargePercent / 100   ※切り捨て
 ─────────────────────────────────────────────
 ご請求額        = 小計 + テーブルチャージ + 深夜料金
 内消費税        = includedTax(ご請求額, taxRatePercent)
```

- **この計算はこの 1 箇所だけ。** 画面は getter を読むだけにする。
- 単価・割増率・税率は**来店時点の設定をコピー**して伝票に保存する。
  設定を変えても、すでに開いている伝票の金額は変わらない。
- 深夜料金の判定は `ShopSetting.isLateNight()`。23:00〜翌 5:00（営業日切り替え時刻）を深夜とみなす。
  単純に `t >= 23:00` と書くと深夜 1:00 が対象外になるため。
- ホール画面でスタッフが深夜料金を**外せる**（サービス対応のため）。

### 4.3 注文番号

- 営業日ごとに `ShopSetting.orderNumberStart`（既定 101）から連番。
- 採番は `DailyCounter` を **悲観ロック（`SELECT ... FOR UPDATE`）** して行う。
- 採番だけ `Propagation.REQUIRES_NEW` の別トランザクション。理由は 2 つ:
  1. ロックを握る時間を最短にして同時注文を詰まらせない
  2. 注文本体の保存に失敗しても採番の状態が壊れない
- `DailyCounter` は `Persistable` を実装し、新規なら必ず INSERT になるようにしている。
  そうしないと「初回同時注文でカウンタが巻き戻る」競合が起きる。
- **番号は飛んでもよい。** 番号を再利用するほうが事故になる。

### 4.4 営業日

- 暦の日付ではなく「営業日」で集計する。
- `ShopSetting.businessDayCutoverHour`（既定 5 時）より前の注文は**前日の営業日**として扱う。
- 深夜 1 時の注文も「その日の営業」として売上に入る。

### 4.5 受付可否

`ShopSetting.isOrderAcceptable(now)` が唯一の判定。

1. `acceptingOrders = true`（店長が手動で止めていない）
2. 営業時間内（**日をまたぐ営業に対応**。`lastOrderTime < openTime` なら日跨ぎと解釈）
3. 伝票が `OPEN`（会計済みの卓からは注文できない）

### 4.6 カートの再検証（重要）

カートはブラウザのセッションに置かれるため、入れてから注文するまでの間に
値上げ・品切れ・商品削除が起きうる。

`OrderService.placeOrder()` は保存前に必ず `CartService.refresh()` を通し、
1 つでも変化があれば**注文を通さず**、更新後のカートと変更内容を見せて再確認してもらう。

> セッションの値をそのまま信じて会計すると、実際の売価と違う金額で受け付けてしまう。
> ここは金銭事故に直結するので、迷ったら「通さない」側に倒す。

### 4.7 アレルゲン

- **アレルゲンが 1 件も登録されていない商品は「未確認」として扱う。**
  画面には「アレルギーは店舗へお尋ねください」と出し、「小麦不使用」バッジは出さない。
- 「調べた結果ふくまれていない」のか「まだ登録していないだけ」なのかを
  お客さんが区別できないと、誤った安心を与えてしまうため。
- 初期投入データは**意図的に未登録**。店舗が原材料表示を確認して登録する運用。

### 4.8 売上の計上

- 伝票（`TableSession`）が `CLOSED` になった時点で確定。
- 商品別ランキングは `OrderStatus.COMPLETED` の明細から集計（`SalesReportService`）。
  **伝票ベースの総額とはテーブルチャージ・深夜料金のぶんズレる**ので、
  画面上でどちらの数字か分かるようにしている。

## 6. 設計判断とその理由

| 判断 | 理由 | 代替案と却下理由 |
|---|---|---|
| 卓 QR は固定、伝票は来店ごと | QR を貼り替えずに済み、前の客の伝票も見えない | 伝票ごとに QR → 毎回印刷が必要で運用が回らない |
| 伝票の金額計算を 1 クラスに集約 | 会計は間違えると実害。散らばると必ずズレる | 画面ごとに計算 → 表示と請求が食い違う |
| 設定を伝票にコピー | 営業中に設定を変えても既存の伝票が壊れない | マスタ参照 → 会計の証跡として成立しない |
| Thymeleaf（サーバサイド描画） | 画面数が少なく SEO も不要。学習コストが最小 | React/Vue → ビルド構成が増える |
| カートをセッションに置く | ログイン不要の匿名注文で最も単純 | DB に持つ → 匿名ユーザーのゴミデータが溜まる |
| SSE（WebSocket ではなく） | サーバ→ブラウザの一方向で足りる | WebSocket → 双方向は不要なのに実装が重い |
| 明細に価格をスナップショット | 値上げしても過去の伝票が変わらない | マスタ参照 → 会計の証跡にならない |
| 採番専用テーブル + 悲観ロック | 同時注文で番号が重複しない | MAX+1 → 競合状態で重複する |
| `open-in-view: false` | 画面描画中に DB 接続を握らない | true（既定）→ 接続枯渇の温床 |
| 金額は `int` | 円に小数はない。誤差ゼロ | `double` → 金額がズレる |
| QR に UUID トークン | 番号を変えて他卓の伝票を覗けない | 連番 ID → 総当たりで覗ける |
| Lombok を使わない | getter/setter が見えるほうが学習になる | Lombok → 生成コードが見えず混乱する |
| CSS フレームワーク不使用 | 和モダンな見た目を細部まで作り込むため | Bootstrap → どこかで見た画面になる |
| 外部フォント・CDN 不使用 | 店内 Wi-Fi にネットが無くても崩れない | Google Fonts → オフラインで文字化け |

## 7. セキュリティ上の考慮

| 脅威 | 対策 |
|---|---|
| 他卓の伝票を覗かれる | 連番 ID ではなく UUID の `accessToken` で参照（ケイパビリティ URL） |
| CSRF | Spring Security 既定で有効。フォームは `th:action` で自動的にトークンが入る |
| 価格の改ざん | 送信された価格は一切信用せず、必ず DB の現在価格で再計算 |
| 存在しない選択肢の混入 | この商品に属さない選択肢 ID が来たら拒否（`CartService`） |
| 品切れ商品の注文 | カート追加時と注文確定時の 2 回チェック |
| 会計済みの卓からの注文 | `TableSession.isOrderable()` で拒否 |
| パスワード漏洩 | BCrypt ハッシュのみ保存。初期パスワードは自動生成しログに 1 回だけ表示 |
| ユーザー名の存在推測 | 認証失敗メッセージを統一、`hideUserNotFoundExceptions` を有効化 |
| ディレクトリトラバーサル | アップロード名は UUID で作り直し、保存先が上位に出ないか検証 |
| 不正なファイルのアップロード | 拡張子と Content-Type の両方を許可リストで検証。5MB 上限 |
| セッションのメモリ枯渇 | カートに行数・個数の上限（30 種類 / 1 行 20 個） |
| 状態遷移の飛ばし | 画面のボタンだけでなくサーバ側でも `allowedNext()` を検証 |

### 残っているリスク（承知のうえ）

- **同じ店内の別の人**が卓の QR を撮れば、その卓の伝票を見られる。
  店内に貼る性質上これは防げないため、店舗運用で許容する。
- **年齢確認ができない。** 酒類の提供時に店頭で必ず確認する運用が前提。
- SSE の接続はインメモリ保持のため、**アプリを複数台に負荷分散すると通知が届かない**。
  1 台運用が前提。
- 同じ卓に同時に 2 人が QR を読むと、理論上は伝票が 2 つできうる。
  DB の部分一意制約が製品依存になるため採用せず、ホール画面から統合する運用でカバー。
- レート制限を入れていない。公開インターネットに出す場合は要検討。

## 8. 今後の課題

優先度順。

1. **価格の税抜／税込の確定**
   ドリンクは公式サイトに「税抜」と明記されている。投入データはサイト表記のまま。
   **営業に使う前に必ず整理すること。**
2. **アレルゲンの登録**
   全商品が未登録。店舗で原材料を確認して入れる。
3. **DB マイグレーション（Flyway）の導入**
   いまは dev が `ddl-auto: update`、prod が `validate`。
   本番でスキーマを変えるには手動 DDL が必要な状態。
4. **曜日別の営業時間**
   土日は 16:00 開店だが、設定は 1 組しか持てない。
5. **レシート印刷**
   いまは画面表示のみ。ESC/POS 対応のサーマルプリンタ連携があると実用度が上がる。
6. **割り勘・部分会計**
   伝票を分けて会計する機能はない。
7. **画像のリサイズ**
   アップロードした画像をそのまま配信している。
8. **監視・バックアップ**
   H2 のファイルを定期コピーする仕組み。営業データが飛ぶと痛い。
