# ネットワーク設定ガイド — お客さまとスタッフの通信を分ける

最終更新: 2026-08-17

このシステムはアプリ側の対策（認証・CSRF・改ざん検証など）は済んでいますが、
**通信が HTTP（暗号化なし）** のため、スタッフのログインパスワードが
店内 Wi-Fi を平文で流れます。同じネットワークにいる人からは技術的に盗聴できます。

その対策は**コードではなくルーターの設定**で行います。このガイドの通りにやれば
費用ゼロ・コード変更ゼロで塞がります。

---

## ⚠️ 最初に知るべき罠：「ゲストSSID」をそのまま ON にすると注文が止まる

多くのルーターの「ゲスト機能」は **LAN からの完全隔離** が本質です。
ゲストに繋いだ端末は、インターネットには出られますが**店内の機器には一切届きません**。

このシステムはサーバが店内の PC にあるので、
お客さまのスマホがゲスト側にいると **QR を読んでもメニューが開かなくなります**。

> クラウド型 POS（Air レジ等）にこの問題が無いのは、サーバがインターネット上に
> あるからです。自前サーバ構成では「お客さまも店内ネットワークに入る」のが前提になります。

---

## 推奨構成

```
インターネット ─── ルーター
                    ├─ 有線LANケーブル : サーバPC（注文システム）★必ず有線
                    ├─ SSID1（スタッフ用）: 厨房・ホールのタブレット
                    └─ SSID2（お客さま用）: プライバシーセパレーター ON
```

3 つのポイント：

1. **サーバ PC は必ず有線接続にする。**
   安定・速度のためでもありますが、後述のセパレーターの仕組み上、
   有線にしておくと「お客さまからサーバには届くが、無線端末同士は遮断」が成立します。

2. **お客さま用は「ゲストモード」ではなく「2 つ目の SSID（マルチ SSID）」を使い、
   プライバシーセパレーター（ネットワーク分離）を ON にする。**
   - プライバシーセパレーター＝「無線クライアント同士の通信を遮断する」機能。
     多くの機種で、無線→**有線**への通信は通します。
   - つまり：お客さま → サーバ PC（有線）は届く ✓
     お客さま → 別のお客さまのスマホ ✗
     お客さま → スタッフのタブレット（無線）✗
   - これが今回やりたいことのすべてです。

3. **スタッフ用 SSID のパスワードは店内に掲示しない。**
   お客さま用 SSID のパスワードは卓の POP に書いて構いません（注文に必要なので）。

### 機種ごとの機能名（設定画面で探す言葉）

| メーカー | 使う機能 | 注意 |
|---|---|---|
| Buffalo | 「マルチSSID」＋「プライバシーセパレーター」 | 「ゲストポート」は LAN 遮断型のことが多く**不向き** |
| NEC Aterm | 「セカンダリSSID」＋「ネットワーク分離機能」 | セカンダリ側だけ分離を ON |
| TP-Link | 「ゲストネットワーク」 | 「ローカルネットワークへのアクセスを許可」に**チェックを入れる**＋「ゲスト同士の通信を許可」は外す |
| その他 | 「SSID2」「AP隔離」「クライアント分離」等 | 名前は違っても仕組みは同じ |

> 機種によって挙動に差があります。**設定したら必ず下のチェックリストで確認**してください。
> どうしても「分離」と「サーバへの到達」を両立できない機種の場合は、
> 全員同じ SSID のままでも「プライバシーセパレーターだけ ON」にする価値があります
> （サーバが有線なら注文は動き、無線端末同士の盗聴は塞がります）。

## サーバ PC に有線 LAN を引けない場合（店の構造的に無理なとき）

ルーターと PC の位置が離れていてケーブルを這わせられない店は多いです。選択肢は 3 つ。

### 選択肢1（推奨）: PLC アダプタ ―「コンセントが LAN ケーブルになる」

**PLC（電力線通信）アダプタ**は、家の電気配線を LAN ケーブル代わりに使う機器です。
ペアで 5,000〜8,000 円程度（TP-Link・Panasonic など）。

```
ルーター ─LANケーブル─ PLC親機 ─(壁の中の電気配線)─ PLC子機 ─LANケーブル─ サーバPC
          （コンセントに挿す）                    （コンセントに挿す）
```

- 配線工事ゼロ。コンセントに挿してケーブルを 2 本挿すだけ
- ネットワーク上は**正真正銘の「有線」**なので、このガイドの構成
  （セパレーターで無線同士を遮断しつつ、客→サーバは届く）がそのまま成立する
- 弱点: 古い電気配線・分電盤をまたぐ配置だと速度が落ちる。
  ただしこのシステムの通信量はごく小さいので、まず問題にならない

### 選択肢2: 中継機・メッシュ子機の「有線ポート」を使う

Wi-Fi 中継機やメッシュの子機には LAN ポートが付いている機種が多く、
PC をそこにケーブルで挿すと「PC ⇔(ケーブル)⇔ 子機 ⇔(無線)⇔ ルーター」になります。

- 機種の組み合わせによってセパレーターとの相性が変わるので、
  **導入したら必ず下のチェックリストで実測**すること（届く/届かないが機種依存）

### 選択肢3（機材ゼロ）: 分離をあきらめ、リスクを理解して受け入れる

全員同一ネットワークのまま運用します。そのときのリスクの実態を正確に：

- 客用 Wi-Fi のパスワードは卓に掲示する（注文に必要）ので、
  「店に来た人は誰でもネットワークに入れる」状態になる
- その中に本気の攻撃者がいれば、スタッフのログインパスワードを盗聴できる。
  可能性は低いが、ゼロではない

受け入れる場合の緩和策：

1. **管理作業（/admin）はサーバ PC 自身のブラウザでやる**
   （`http://localhost:8080/admin`）。localhost の通信は Wi-Fi を一切通らないので、
   **管理者パスワードは完全に盗聴不能**になる。一番強い緩和策
2. 厨房・ホール端末のログインは**開店前に済ませておく**
   （パスワードが電波に乗る回数そのものを減らす）
3. スタッフのパスワードは長くする（8 文字の最低制限より長く）

迷ったら**選択肢1**。数千円で構造の問題が消えます。

## 「スマホから開けない」ときの調べ方（2026-08-18 の実話つき）

初めてスマホから開こうとすると、まず十中八九つながりません。
原因は 1 つではなく積み重なっているので、**上から順に 1 つずつ**潰します。
勘で設定をいじると、直ったのか別の原因に移っただけなのか分からなくなります。

### 切り分けの順番

| # | 確認すること | 調べ方 | ダメなときの直し方 |
|---|---|---|---|
| 1 | QR の URL が `localhost` になっていないか | PC で `/admin/qr` を開いてリンク先を見る | `application.yml` の `app.base-url` を PC の LAN IP に |
| 2 | PC とスマホが**同じ SSID** にいるか | スマホの Wi-Fi 設定 | 同じにする（2.4GHz と 5GHz が別名の機種に注意） |
| 3 | その SSID が Windows で **Private** 扱いか | `Get-NetConnectionProfile` | `Set-NetConnectionProfile -InterfaceAlias "Wi-Fi" -NetworkCategory Private` |
| 4 | ping が届くか（ネットワーク層） | 下の adb 参照 | 届かなければルーターの「ネットワーク分離」を疑う |
| 5 | TCP 8080 が通るか（アプリ層） | 下の adb 参照 | **拒否ルールを疑う（下記）** |

### ★ 最大の罠：Java の「拒否」ルール

Windows ファイアウォールは **「拒否」が「許可」より常に強い**というルールで動きます。
だから許可ルールを正しく作っても、拒否ルールが 1 本あるだけで永久に通りません。

そして **アプリを初めて起動したときに出る「Windows セキュリティの重要な警告」で
『キャンセル』を押すと、拒否ルールが自動生成されます。**
これが残っていると、症状はこうなります:

- ping は通る（ICMP はプログラムと無関係なので素通り）
- でも 8080 だけタイムアウト（Java が待つポートなので拒否される）

確認:

```powershell
Get-NetFirewallRule -DisplayName "OpenJDK Platform binary" | Select-Object Name, Action, Profile
```

`Action = Block` の行があれば、それが犯人です。名前が
`TCP Query User{...}\...\java.exe` の形をしていれば、まさに上記のダイアログ由来です。

> **「OpenJDK Platform binary」って何？** 見慣れない名前ですが、正体は
> このプロジェクト用に入れた `java.exe` そのものです。
> Windows はファイアウォールのルール名に、その exe が自分で名乗っている
> 「ファイルの説明」を使います。java.exe の説明が `OpenJDK Platform binary`
> なので、こう表示されるだけ。怪しいものが勝手に入っていたわけではありません。
> （確認: `(Get-Item "$env:JAVA_HOME\bin\java.exe").VersionInfo.FileDescription`）
>
> **なぜ「キャンセル」で拒否になるのか。** あのダイアログの
> キャンセル／×／Esc は「あとで決める」ではなく **「許可しない・以後もそうする」**
> として記録されます。しかも TCP と UDP の 2 本が同時に作られます。
> 別ウィンドウの裏に出ていて気づかずに Enter や Esc を押した、でも同じことが起きます。

削除するときは **必ず 1 行で**書いてください:

```powershell
Get-NetFirewallRule -DisplayName "OpenJDK Platform binary" | Where-Object Action -eq "Block" | Remove-NetFirewallRule
```

> ⚠️ **絶対にやってはいけないこと**
> `Remove-NetFirewallRule` を**条件なしで単独実行する**と、
> **ローカルのファイアウォールルールが全部消えます**（実際に消しました）。
> 複数行に分けて貼ると、途中で改行が切れてこの単独実行が起きます。削除系は 1 行で。
>
> 全部消してしまったときの復旧（管理者 PowerShell・1 行）:
> ```powershell
> netsh advfirewall reset
> ```
> Windows 標準ルール（162 本）は読み取り専用領域にあるので必ず戻ります。
> ただし他アプリが作った個別ルールは戻らず、次回使用時に許可ダイアログが再度出ます。
> なおこの状態でもファイアウォール自体は有効で、受信は既定でブロックのため
> 「穴が空く」のではなく「全部閉まる」方向に倒れます。

### 再発防止：先に「許可」を作っておく（設定済み）

ダイアログは**まだ決めていないプログラム**にだけ出ます。
逆に言えば、先に許可ルールを作っておけば**二度と出ない**＝押し間違いようがない。
2026-08-18 に次の 2 本を作成済みです。

| ルール名 | 対象 |
|---|---|
| `Komeko Order 8080` | TCP 8080（プログラム不問）／Private |
| `Komeko Order (java 8080)` | この java.exe の TCP 8080 のみ／Private |

作り直すときは（管理者 PowerShell・1 行）:

```powershell
New-NetFirewallRule -DisplayName "Komeko Order (java 8080)" -Direction Inbound -Program "C:\Program Files\Eclipse Adoptium\jdk-21.0.12.8-hotspot\bin\java.exe" -Protocol TCP -LocalPort 8080 -Action Allow -Profile Private
```

> **JDK を更新したら作り直しが必要です。** ルールは exe のパスを見ているので、
> `jdk-21.0.12.8-hotspot` が別バージョンに変わると一致しなくなり、
> ダイアログが再び出ます。そのときは必ず「**アクセスを許可する**」を選ぶこと。

### スマホを USB で繋いで原因を特定する（adb）

推測をやめて事実で判定したいときはこれが最短です。
Google 公式のポータブル版を `C:\Users\zaki\tools\platform-tools` に置いてあります。

スマホ側の準備（1 回だけ）:
1. 設定 → デバイス情報 →「ビルド番号」を 7 回連打（開発者モード解放）
2. 設定 → システム → 開発者向けオプション →「USB デバッグ」ON
3. USB 接続 →「USB デバッグを許可しますか？」で許可

```powershell
$adb = "C:\Users\zaki\tools\platform-tools\adb.exe"
& $adb devices                                        # device と出れば OK
& $adb shell ip route                                 # スマホがどの経路で通信しているか
& $adb shell ping -c 4 192.168.1.4                    # ネットワーク層は生きているか
& $adb shell 'printf "GET / HTTP/1.0\r\n\r\n" | toybox nc -w 8 192.168.1.4 8080'   # アプリ層
```

最後の行で `HTTP/1.1 200` が返れば**サーバ側は完全に正常**で、
以降はスマホのブラウザ側（後述）だけを疑えばよくなります。

スマホの画面をそのまま見ることもできます（ロック中だと真っ黒なので注意）:

```powershell
& $adb exec-out screencap -p > phone.png
```

> `adb devices` に何も出ないのに Windows の[デバイス マネージャー]には
> 「ADB Interface」が見えている場合、adb 用の目印（GUID）が未登録です。
> 管理者 PowerShell で対象の `Device Parameters` に
> `DeviceInterfaceGUIDs = {F72FE0D4-CBCB-407d-8814-9ED673D0DD6B}` を書き、
> `pnputil /restart-device "<InstanceId>"` で読み直させると認識します。

### サーバに届いているかを目で見る（アクセスログ）

`application-dev.yml` で Tomcat のアクセスログを有効にしてあります。

```
data\tomcat\logs\access_log.YYYY-MM-DD.log
```

ここに**スマホの IP の行が出る**＝リクエストはサーバまで届いている（＝アプリ側の問題）。
**出ない**＝途中で消えている（＝ネットワーク・ファイアウォール・スマホ側の問題）。
この二分ができるだけで、調査時間が桁で変わります。

### ネットワークが正常なのに開けないとき（スマホ側の容疑者）

- **画面がロックされている** … Chrome は裏で止まったまま。ロック解除すれば読み込む
- **HTTPS への自動格上げ** … Chrome 設定 → プライバシーとセキュリティ →
  「常に安全な接続を使用する」を OFF。アドレスバーが `https://192.168...` なら確定
- **モバイル回線への横流し** … Wi-Fi が怪しいと判断すると通信だけ 4G/5G に流す機種がある
  （「スマートネットワーク切替」等）。モバイルデータを一時 OFF にして切り分ける
- **カメラ以外の QR リーダー** … LINE などはアプリ内ブラウザで開き、挙動が異なる

## あわせてやること：サーバ PC の IP を固定する

QR コードには `http://192.168.x.x:8080/t/...` のように **PC の IP アドレス**が入っています。
DHCP のままだと再起動で IP が変わり、**印刷済みの QR が全部無効になります**。

ルーターの設定画面で「**DHCP 固定割当（IP アドレス予約）**」を探し、
サーバ PC の MAC アドレスにいまの IP を割り当ててください。
（PC 側で固定するより、ルーター側で予約するほうが事故が少ないです）

## アプリ側の第二の錠：スタッフ画面の「接続元制限」

ネットワークの分離とは**別に・独立して**、アプリ自身にも関所があります。
`application.yml` の `app.staff-access.allowed-ips` に IP を書くと、
スタッフ用 URL（`/login` `/kitchen` `/hall` `/admin`）は**その IP からしか開けなくなります**。

```yaml
app:
  staff-access:
    allowed-ips:
      - 192.168.1.21      # 厨房タブレット（ルーターで固定予約した IP）
      - 192.168.1.22      # ホールタブレット
```

- お客さまのスマホからは、**たとえパスワードを知っていてもログイン画面自体が出ない**（403）
- パスワード（知っているか）と接続元（どこから来たか）の**独立した二重ロック**になる
- サーバ PC 自身（localhost）は常に許可 ＝ 設定を書き間違えても本体の前に座れば直せる
- 空のままなら制限なし（従来どおり）

手順：①ルーターの DHCP 固定割当でスタッフ端末の IP を予約 → ②yml に列挙して再起動 →
③自分のスマホ（許可外）で `/login` を開いて 403 になることを確認。

> **正直な限界**：IP は同一 LAN 上の本気の攻撃者には偽装され得ます（ARP スプーフィング）。
> つまりこれは暗号のような絶対の壁ではなく「破るべき錠を 1 つ増やす」対策です。
> ネットワーク分離（上の構成）と併用したときに最も効きます。

## それでも残るもの（正直な整理）

- お客さま用 SSID に入った人は、**サーバの注文ページには届きます**（届かないと注文できないので当然）。
  サーバ側はもともと「客に開いていい URL」しか許可していないため（SecurityConfig）、
  ここは追加のリスクにはなりません。
- スタッフ端末が**有線**の場合、セパレーターの保護対象外になる機種があります。
  上のチェックリスト 3 番で必ず確認してください。
- 将来インターネットに公開する（店外から注文できるようにする）場合は、
  この構成では足りません。HTTPS・レート制限・監視が必須になります。
