### 実測だけでは崩れを捕まえられなかった

今日いちばんの失敗。DOM を測って「設計どおり」と報告した画面を、
店主がスクリーンショットを送ってきて 2 か所の崩れを指摘した。

- 写真の左右に 18px の隙間（`.card` が `.container` の余白の中にいた）
- ボタンが枠からはみ出し（`.cart-bar` の左右余白 32px ぶん幅が足りない）

どちらも「幅 342」「高さ 56」という数字は合っていた。
**測った要素が正しくても、その外側の入れ物がずれていると気づけない。**

`mcp__claude-in-chrome__computer` の screenshot は、この環境では
`params.clip.scale` のエラーで動かなかった。代わりに使えたのは:

- 店主にスクリーンショットをもらう（いちばん速い。2 か所とも一発で特定できた）
- 要素の `getBoundingClientRect()` を**親からの相対位置**で出す
  （幅だけでなく「モーダルの左端から何 px か」を必ず見る）

### 実測に使っている手順

`localhost:8090` は書き出した HTML（`AllScreensDumpTest`）、
`localhost:8080` は動いているアプリ。ブラウザのタブを **同じオリジン**に
合わせてから iframe を作らないと `contentDocument` が null になる。

```js
// 幅 390px の実機と同じ条件を作る
const f = document.createElement('iframe');
f.style.cssText = 'position:fixed;left:0;top:0;width:390px;height:844px;border:0;visibility:hidden';
f.src = '/menu';
```

★ **この Chrome はページによってスクロールバーが 23px を占める。**
縦に長い画面は `width:413px`（390 + 23）にしないと中身が 390 にならない。
短くてスクロールしない画面（サービスなど）は 390 のままでよい。
`d.documentElement.clientWidth` を必ず出力して、390 になっているか確かめること。

## 1. 作りかけ・未決のもの

### 1-1. トッピングの残り 3 行が読めていない（要・店主の回答）

設計「暗05」のトッピングは 6 行あるが、枠が 190px で切ってあるため
**画面に写っているのは 3 行だけ**。下 3 行の品名と金額は取り出せなかった。

```
読めた    チーズ +¥180 ／ 餅 +¥150 ／ 目玉焼き +¥120   → 実装済み
読めない  あと 3 行
```

`get_screenshot` に `contentsOnly: true` を付けても、
クリップされた子は描画されない（19px の切れ端が返るだけ）。
`get_design_context` なら文字が取れるはずだが、
それを呼ぶ前に figma-design-to-code スキルを読む決まりがあるので、今日は回さなかった。

値段を勝手に決めるのは避けた。**次にやるなら、まず店主に 3 行を聞く。**

### 1-2. 「4 種類お選びください」で同じ味を複数選べるか（要・店主の回答）

店主から出た疑問がそのまま止まっている。

> ソース 3 つ、ごま油 1 つの場合それだとエラーが起きるのか

**答えはエラー以前に「入力できない」。**
選択肢はチェックボックスで、同じ味は 1 回しか選べない。
「4 種類」は文字どおり違う味を 4 つ選ぶ設定になっている。

店主に確認してもらっている問い:

- 8 個を 4 種類（1 味 2 個ずつ）で回しているなら、いまのままで正しい
- 「ソースだけ多め」を受けているなら、味ごとに個数を持つ作りに変える必要がある

**後者になった場合は保存の形から変わる。**いまは「どの選択肢を選んだか」しか
持っていないので、個数を置く場所が要る（注文明細のオプション行・厨房の表示・伝票の表示）。
Figma のモーダルもチェックボックスで描かれているので、
設計としては「違う味を選ぶ」で確定しているように見える、とは伝えてある。

### 1-3. 商品モーダルの背が設計より高い（未決）

設計の本文は「品名と価格」1 行だけ。実装は説明文・おすすめバッジ・
焼き上がりの目安が入るぶん高く、品によっては「やめる」がスクロールしないと出ない。

右上に × を足して凌いでいる（設計には × は無い）。
店主から「詳細のデザインは良かったのでそのままに」と言われているので、
情報を削るかどうかは聞いてから。**勝手に設計どおり 1 行へ詰めないこと。**

### 1-4. カテゴリの並び順（2 回上がって、2 回とも流れた）

店主が「カテゴリーの並び順が分かりにくいから少し話し合おう」と言ったまま、
別の話に移って戻ってきていない。こちらから振り直す価値がある。

聞くべきは 2 つ。

- 並べたいのは**カテゴリそのものの順番**か、**お客さま側のタブの中の順番**か
- 数字（10, 20, 30…）をやめて**上下ボタン**にしたいか、数字は残したいか

調べた事実: `sortOrder` は手入力で自動採番が無く、新しい商品は 0 で入る。
同じ値のときは id 順になる。

### 1-5. サービスの品の並びが、既存 DB だけ設計と違う

種のコードは設計順（… 灰皿 → 領収書 → 塩コショウ）に直したが、
**すでに DB に入っている `sortOrder` は上書きしない**作りなので、
`komeko-demo-full` では 塩コショウ → 領収書 のまま。

店主には「管理画面 → 商品 から並べ替えれば直る」と伝えてある。
作り直してよければ、サービスのカテゴリを消して再起動すれば
`backfillServiceItems` が設計順で作り直す。

### 1-6. 未 push が 13 コミット

`main` が `origin/main` より 13 進んでいる。push は外向きの操作なので、
店主に言われてから実行すること。今日はまだ聞いていない。

`AdminMenuItemController.list`。店主が並行で書いていた検索（`?q=`）の続き。

これはアプリの弱点で、隠さずに見せている。直すなら
「価格 0 の品は販売再開できない」といった歯止めが要るが、
サービスの品（お水など）が ¥0 で注文される作りなので、
価格 0 を一律で弾く実装にはできない。設計から決め直す話。

## 4. コードに書いていない判断・前提

### 4-1. 「アレルギーは店舗へお尋ねください」を消したのは店主の指示

もとは「食物アレルギーは命に関わるので迷ったら安全側」という判断で入っていた札。
それを覆した理由は**全品がアレルゲン未登録なので、全部の行と札に付いて
画面が埋まり、肝心のアレルゲン表示のほうが読み飛ばされる**から。

再導入の話が出たら、この経緯を先に出すこと。
「安全側だから戻そう」だけで戻すと、また同じ状態になる。
登録が進めば札は自然に減るので、**アレルゲンの登録が進んだ時点で再検討**が筋。

### 4-2. 「詳細のデザインは良かったのでそのまま」

商品モーダルの中身は変えるな、という明示の指示（§1-3）。

### 4-3. 大分類は「食べ物か、飲み物か」の 1 本だけ

設計の上の帯は お食事／ドリンク／サービス／伝票・会計 だが、
カテゴリが持つ大カテゴリ名は 粉もの／鉄板料理／一品料理／ドリンク で 1 段ずれている。

**列を足さず、「大カテゴリがドリンクかどうか」で分ける**判断をした。
お客さまから見た区別はその 1 本だけ、という理由。
店主がこの名前を変えるとドリンクのタブが空になる（画面には「準備中です」と出る）。
**設計を作り込むなら、ここは列を足す作り直しの候補。**

### 4-4. Figma のアイコンは、ベクタと画像が混ざっている

お水・取り皿・灰皿・塩コショウ の 4 つは **64x64 の PNG** で、ベクタが無い。
似せて描き直したら店主に「違う」と言われた。手で描いた形は一致しない。

Figma の画像をそのまま `/images/icons/` に置いている。
`currentColor` が効かないが、タイルではきつね色固定なので実害が無い、という判断。
**規約（インライン SVG に寄せる）から意図的に外している。**

### 4-5. デモ DB とプロセスの状態

```
data/komeko-demo-full.mv.db   いま 8080 が使っている。今日作り直したもの
data/komeko-live2.mv.db       中途版のコードで仕込んだので 9/1〜9/4 に穴がある。使わない
data/komeko-live.mv.db        8/31 まで。中身は未確認
```

起動しているのは 8080（`komeko-demo-full`）だけ。8090（書き出し HTML の配信）は
別に立てていたが、いまは落ちているかもしれない。

**`komeko-demo-full` は作り直した DB なので、管理者パスワードが変わっている。**
初回起動のログにしか出ない。分からなくなったら
`docs\引き継ぎ.md` 末尾の復旧手順（DB を消して作り直す）を使う。
ゲストログイン（`app.guest-login=true`）なら厨房・ホール・品切れは見られるが、
**売上・仕入れ・税理士は ADMIN でないと開けない。**

### 4-6. ブランチが途中で変わっている

作業の途中で `feature/hall-table-orders` から `main` に切り替わった。
店主が別のターミナルで `main` を checkout して `origin/main` を取り込み、
そのうえに自分のコミット（家賃・商品検索）を積んでいる。

**店主は並行して同じリポジトリを触っている。**
ビルドが通らないときは、自分の変更だけでなく相手の作業中コードを疑うこと。
今日は `AdminMenuItemController` が実質 final でないラムダ参照で
コンパイルできない時間帯があった。

### 4-7. 実測は必ず「稼働中のアプリ」でも取る

書き出した HTML（8090）だけで確認すると、
画像のハッシュ付きファイル名が解決できず「画像が読めない」といった
書き出し側だけの現象に振り回される。**最後は 8080 で測る。**

### 4-8. デモデータは「説明したい状態」を混ぜてある

きれいに揃ったデータにしない、というのが `DemoDataSeeder` と
`InventoryDemoDataSeeder` から受け継いでいる方針。
今日は時価の 3 状態（正しい運用／入れ忘れ／出荷時）を並べた。
**デモを「全部正常」に直したくなったら、この方針とぶつかることを思い出すこと。**
