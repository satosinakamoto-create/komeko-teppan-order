# 公開デモのデプロイ

ポートフォリオを見に来た方に**実際に触ってもらう**ための公開手順。
実店舗の運用（prod）とは目的も設定も別なので、`demo` プロファイルを用意してある。

| | 目的 | DB | データが消えたら |
|---|---|---|---|
| `dev` | 手元で作りながら動かす | H2 ファイル | 困る（バックアップあり） |
| `prod` | 実店舗 | PostgreSQL | **絶対に困る** |
| `demo` | 誰でも触れる公開版 | H2 ファイル | **むしろ好都合**（毎回作り直す） |

---

## 1. 設定するのは環境変数 2 つだけ

ホスティングの管理画面で設定する。

| 環境変数 | 値 | いつ入れるか |
|---|---|---|
| `SPRING_PROFILES_ACTIVE` | `demo` | **作成時**（必須） |
| `APP_BASE_URL` | `https://＜公開URL＞` | 作成後でよい |
| `INITIAL_ADMIN_PASSWORD` | デモ専用の使い捨て | 入れておくと楽（下記） |

### いま動いているもの

| | |
|---|---|
| URL | https://komeko-teppan-order.onrender.com |
| サービス | Render / Docker / Free / Singapore |
| リポジトリ | `satosinakamoto-create/komeko-teppan-order`（main への push で自動デプロイ） |

### `INITIAL_ADMIN_PASSWORD` を入れておく理由

`DataSeeder` は管理者がいなければ作り、**パスワード未指定ならランダムに生成して
ログに 1 回だけ出す**。手元ではこれで困らない。`data\` の DB が残るので、
最初に決まったパスワードをずっと使えるからだ。

Render の無料枠は違う。15 分の無通信でスリープし、次の起動は**まっさらなコンテナ**、
つまり空の DB になる。起動のたびに `DataSeeder` が走り、
**パスワードが毎回作り直される**。

つまり「公開前に管理者パスワードを変更する」が原理的に成立しない。
変更しても次のスリープ復帰で消える。ADMIN で入りたければ、
そのたびに Render のログから生成値を拾うことになる。

環境変数に入れておけば、起動のたびに同じ値になる。
**値はコードにも yml にも書かず、Render の Environment 画面にだけ置くこと。**

> ゲストは代わりにならない。`GuestLoginController` は `StaffRole.STAFF` 固定で、
> `/admin/**` の設定変更系には入れない（それが狙いなので、ここは変えない）。

### `APP_BASE_URL` は後回しでいい

公開 URL はサービスを作った**あとに**発行されるので、
最初の 1 回目は入れようがない。

そのため `application-demo.yml` の既定値を `${APP_BASE_URL:}`（空）にしてある。
未設定でも起動し、QR の飛び先が `http://localhost:8080` のあいだは
QR 画面の上部に「この値のままでは使えません」と警告が出る。

> はじめは `${APP_BASE_URL}` と書いていた（既定値なし）。
> これだと変数が無いとき Spring が
> `Could not resolve placeholder 'APP_BASE_URL'` で**起動そのものを中止**する。
> 表示用の URL が分からないというだけでシステム全体が立ち上がらないのは、
> 釣り合いが取れていない。**止めるのではなく、気付ける形にして動かす。**

### `APP_BASE_URL` がすべてを決める

**この値が QR コードに焼き込まれる。**

```
QR の中身 = ${APP_BASE_URL}/t/{その卓のトークン}
```

手元の LAN アドレス（`http://192.168.1.4:8080`）のままだと、
QR を読んでも外からは開けない。QR ページの「この卓のお客さま画面を開く」も同じ。

**正しく設定すれば、見に来た方が自分のスマホで QR を読んで注文できる。**
デモとしてはこれがいちばん強い。

> `https://` を付けること。付け忘れると混在コンテンツでブラウザに止められる。

## 2. `demo` プロファイルが自動でやること

`application-demo.yml` に書いてある。手で設定する必要はない。

- **ログイン画面に「ゲストで参加する」を出す**（`app.guest-login`）
- **起動時に営業中の状態を作る**（`app.demo-data`）
  厨房ボードが 3 列とも埋まり、在庫の残数・売り切れも映る
- **24 時間受付にする**
  実店舗の営業時間は 17:30〜翌 1:30。そのままだと昼間に見に来た方は何も注文できない
- **H2 のファイル DB を使う**（PostgreSQL を用意しない）
- **バックアップを止める**（消えて困るデータが無い）
- **H2 コンソールを閉じる**（誰でも触れる場所に DB の入口を出さない）

### 再起動でデータが消えるのは、むしろ好都合

無料ホスティングの多くは再起動でファイルが消える。
本来は困った性質だが、デモに限っては

- 誰かが注文を荒らしても、次の再起動できれいに戻る
- DB の契約も期限も要らない

消えて困るデータが最初から無いので、この割り切りが成立する。

## 3. Docker で動かす

リポジトリ直下の `Dockerfile` をそのまま使える。Render / Fly.io / Railway など Docker が使えるところならどこでも。

マルチステージにしてあるので、最終イメージに Maven もソースも入らない。
イメージが小さいほど起動が速く、**無料枠のコールドスタートが短くなる**。

メモリは `-XX:MaxRAMPercentage=70` を指定済み。
無料枠は 512MB のことが多く、指定しないと JVM がヒープを取りすぎてコンテナごと止められる。

### 非 root で動かすなら、書き込み先の所有権まで含めて一組

最初の Dockerfile は `USER komeko` に切り替えた**あとで** `mkdir -p /app/data` を書いていた。
`WORKDIR /app` は root が作る（所有者 root・755）ので、
`mkdir` が Permission denied で落ち、**docker build がそこで止まった**。

仮にビルドが通っても起動できない。`/app/data` が root 所有のままだと

- H2 が `./data/komeko-demo` を作れない
- `ImageStorageService` はコンストラクタで `Files.createDirectories` を呼び、
  失敗すると例外を投げる（Bean が作れず、アプリごと起動失敗）

`mkdir` と `chown -R komeko:komeko /app` を `USER` 切り替えの前に置いて解決。
**権限を下げるだけでは足りず、下げた先に必要な権限を渡すところまでが一組。**

### タイムゾーンはコードで固定する（環境変数に頼らない）

コンテナの既定は UTC。このアプリは営業日の切り替え（5:00）・ラストオーダー・
深夜料金をすべて**日本時間の壁時計**で判断するので、UTC のままだと 9 時間ずれる。

厄介なのは**例外が出ない**こと。厨房ボードは「その営業日ぶん」しか表示しないので、
**起動時に入れたデモの注文が 1 件も出ない**という形でだけ現れる。

> **踏んだ事故（2026-08-22）**: Dockerfile に `ENV TZ=Asia/Tokyo` と
> `-Duser.timezone=Asia/Tokyo` を二重に指定してあったのに、
> 本番（Render）では**どちらも効いておらず UTC で動いていた**。
> JST 13 時の伝票に深夜料金 10% が乗り、売上の営業日も 1 日ずれていた
> （UTC 23:00〜05:00 = **JST 8:00〜14:00** なので、日本の日中に毎日出る）。
> ホスティング側の環境変数や起動コマンドは画面の操作ひとつで消え得る。
>
> このため `KomekoOrderApplication` の static イニシャライザで
> `TimeZone.setDefault(Asia/Tokyo)` を**コードで**固定した。
> Dockerfile の指定は残してあるが、あれは保険であって本体ではない。
> Render 側の環境変数がなぜ効いていないかは未解明（ダッシュボードの
> Docker Command 上書きが怪しい）。コード固定後はどちらでも正しく動く。

## 4. 眠らせない

無料ホスティングは無通信が続くとサーバを眠らせる。
次に開いた人は 30〜40 秒待たされる。**採用担当は待たない。**

`/ping` が `ok` とだけ返す軽い入口なので、外から定期的に叩いて起こしておく。

> **アプリの中にタイマーを置いても無意味。**
> 眠っている間はそのタイマー自体が止まっている。自分で自分は起こせない。

### 何で叩くか

| | 良い点 | 注意 |
|---|---|---|
| **cron-job.org** | 無料・**時間帯を指定できる**（8〜17 時だけ、など） | おすすめ |
| UptimeRobot | 無料・落ちたらメールで知らせてくれる | 24 時間叩くので、Render の無料インスタンス時間を使い切りやすい |
| GitHub Actions | すでに使っているなら手軽 | private リポジトリだと**分数を使い切る**（1 回 15 秒でも 1 分として課金。10 分おきで月 1,800 分 ≒ 無料枠 2,000 分）。時刻も 5〜15 分ずれる。60 日放置で自動停止 |

### 24 時間叩いてはいけない理由は、もう一つある

`DemoDataSeeder` は**起動時に 1 回だけ**走る。
一方、厨房ボードは `OrderService.kitchenBoard()` が
`currentBusinessDate()` で**その営業日ぶん**に絞り込む。

つまりインスタンスが 5:00（営業日の切り替え）を跨いで生き続けると、
起動時に入れたデモの伝票は前営業日のものになり、**ボードが 3 列とも空になる**。
再シードは走らない（開いている伝票があると `seed()` は何もせずに帰る）。

夜のあいだ眠らせておけば、朝の最初のアクセスで起動し直され、
その日の営業日でデモデータが入り直る。
**「8〜17 時だけ叩く」は節約のためだけの設定ではなく、ボードを埋めておくための設定でもある。**

**時間帯を絞るのが要点。** Render の無料インスタンス時間はアカウント全体で月 750 時間程度。
24 時間起こすと 1 サービスで月 730 時間になり、2 つ動かした時点で破綻する。
8〜17 時なら 1 サービス月 300 時間で、2 つでも収まる。

### 登録の記録

**この設定は cron-job.org 側の作業なので、リポジトリには何も残らない。**
コードを見ても設定済みか分からず、**登録してあっても勝手に止まる**（下記）。
状態が変わったらここを更新すること。

| 項目 | 状態 |
|---|---|
| cron-job.org への登録 | ✅ **登録済み・稼働中**（2026-08-25 12:45 に復旧） |
| ジョブ名 | `komeko-order wake`（透明麻雀は `toumei-mahjong wake`） |
| 最終確認日 | 2026-08-25 12:45（TEST RUN で 200 OK / 555ms） |
| コンソール | https://console.cron-job.org/ |

設定値:

| 項目 | 値 |
|---|---|
| URL | `https://komeko-teppan-order.onrender.com/ping` |
| Crontab | `*/10 8-17 * * *`（10 分ごと・8〜17 時） |
| タイムゾーン | Asia/Tokyo |
| 失敗通知 | 3 回連続で失敗したらメール |

### ⚠️ 「登録した」だけでは足りない。止まっていないかを見ること

**2026-08-25 に発覚**: 登録はしてあったが、**2 件とも無効化されて 4 日間止まっていた**。
cron-job.org は連続で失敗したジョブを自動で無効化する。
8/21 12:10 に komeko が `output too large`、透明麻雀が `HTTP error` で失敗し、
そのまま `Enable job` が OFF に落とされていた。

その結果どうなったか。**8/25 12:30 に `/ping` を叩いたら 1 回目が 39.6 秒**（2 回目は 0.22 秒）。
昼間なのに完全に眠っていた。この状態で採用担当がリンクを踏めば、40 秒待たされる。

`/ping` 自体は正常（200・`text/plain`・本文 2 バイトの `ok`）で、
コードには何の問題も無かった。**リポジトリの外で静かに壊れていた**。

### なぜ「また止まる」のか — 構造的にタイムアウトする

**cron-job.org のタイムアウトは最大 30 秒**（画面に「The maximum timeout is 30 seconds」と出る。
60 秒を入れると弾かれる）。一方 **Render のコールドスタートは実測 39.6 秒**。

つまり **眠っている状態で叩かれると、必ずタイムアウトして失敗する。**

毎朝 8:00 の初回は、前日 17:00 から眠っているので必ずこれに当たる。
ただしその失敗したリクエスト自体が起動の引き金になるので、8:10 の回は成功する。
**「毎朝 1 回失敗 → 以降は成功」が正常な姿**で、これは設定ミスではない。

問題は、Render 側の障害やデプロイが重なって失敗が続いたときに、
cron-job.org が自動でジョブを無効化してしまうこと。2026-08-21 に起きたのはこれ。
（8/21 の失敗理由そのものは履歴の保持期間が切れていて確認できなかった。
komeko は `output too large`、透明麻雀は `HTTP error` で、
2 サービスが 2 秒差で別々の理由で落ちている）

### 根本的に直すなら: 起動を 30 秒以内にする

`spring.main.lazy-initialization=true` を Render の環境変数に入れると起動が速くなる。
**これは 2026-08-25 まで危険な設定だった** — グローバル lazy 化で
`ProductionSafetyGuard` の Bean が生成されず、本番の安全装置が丸ごと死んでいた。
`@Lazy(false)` を付けて塞いだので、**いまは安全に使える**。

入れる場合は、コールドスタートが実際に 30 秒を切るかを測ってから判断すること。
切らないなら意味が無い（30 秒はタイムアウトの上限であって、余裕を見るなら 25 秒以下が望ましい）。

### 当面の運用

対処として失敗通知（3 回連続）を有効にしたので、次に止まったらメールが来る。
それでも月 1 回くらいは、昼間に叩いて 1 秒未満で返るか見ておくとよい。

```bash
curl -s -o /dev/null -w "%{time_total}s\n" https://komeko-teppan-order.onrender.com/ping
```

1 回目から 1 秒未満なら叩き役が効いている。40 秒かかるならまた止まっている。
**さっき自分で叩いた直後に測っても意味が無い**（自分で起こしてしまうため）。
確認は「しばらく触っていない状態」で行うこと。

## 5. 公開前のチェック

- [ ] `APP_BASE_URL` が公開 URL（`https://`）になっている
- [ ] QR ページの URL が公開 URL になっている（見れば分かる）
- [ ] ログイン画面に「ゲストで参加する」が出ている
- [ ] ゲストで `/admin/settings` `/admin/staff` が **403** になる
- [ ] **管理者パスワードを変更した**（初期値のまま公開しない）
- [ ] リポジトリを public にするなら、**コミット履歴に鍵が無いか棚卸しした**

## 6. 訪問者がたどる道

```
ポートフォリオの GIF を見る
   ↓
「実際に触ってみる」を押す
   ↓
ログイン画面 →「ゲストで参加する」
   ↓
厨房ボード（すでに注文が並んでいる）
   ↓
サイドバー →「QRコード」
   ↓
「この卓のお客さま画面を開く」（別タブ）／ スマホで QR を読む
   ↓
注文する → 元のタブの厨房ボードに、その場で届く
```

タブを 2 つ並べれば、1 台の PC でも連携が体感できる。
スマホで QR を読んでもらえれば、実店舗とまったく同じ体験になる。
