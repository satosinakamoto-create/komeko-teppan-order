# 公開デモのデプロイ

ポートフォリオを見に来た方に**実際に触ってもらう**ための公開手順。
実店舗の運用（prod）とは目的も設定も別なので、`demo` プロファイルを用意してある。

| | 目的 | DB | データが消えたら |
|---|---|---|---|
| `dev` | 手元で作りながら動かす | H2 ファイル | 困る（バックアップあり） |
| `prod` | 実店舗 | PostgreSQL | **絶対に困る** |
| `demo` | 誰でも触れる公開版 | H2 ファイル | **むしろ好都合**（毎回作り直す） |

---

## 1. 設定するのは環境変数 2 つだけ

ホスティングの管理画面で設定する。

| 環境変数 | 値 | いつ入れるか |
|---|---|---|
| `SPRING_PROFILES_ACTIVE` | `demo` | **作成時**（必須） |
| `APP_BASE_URL` | `https://＜公開URL＞` | 作成後でよい |

### `APP_BASE_URL` は後回しでいい

公開 URL はサービスを作った**あとに**発行されるので、
最初の 1 回目は入れようがない。

そのため `application-demo.yml` の既定値を `${APP_BASE_URL:}`（空）にしてある。
未設定でも起動し、QR の飛び先が `http://localhost:8080` のあいだは
QR 画面の上部に「この値のままでは使えません」と警告が出る。

> はじめは `${APP_BASE_URL}` と書いていた（既定値なし）。
> これだと変数が無いとき Spring が
> `Could not resolve placeholder 'APP_BASE_URL'` で**起動そのものを中止**する。
> 表示用の URL が分からないというだけでシステム全体が立ち上がらないのは、
> 釣り合いが取れていない。**止めるのではなく、気付ける形にして動かす。**

### `APP_BASE_URL` がすべてを決める

**この値が QR コードに焼き込まれる。**

```
QR の中身 = ${APP_BASE_URL}/t/{その卓のトークン}
```

手元の LAN アドレス（`http://192.168.1.4:8080`）のままだと、
QR を読んでも外からは開けない。QR ページの「この卓のお客さま画面を開く」も同じ。

**正しく設定すれば、見に来た方が自分のスマホで QR を読んで注文できる。**
デモとしてはこれがいちばん強い。

> `https://` を付けること。付け忘れると混在コンテンツでブラウザに止められる。

## 2. `demo` プロファイルが自動でやること

`application-demo.yml` に書いてある。手で設定する必要はない。

- **ログイン画面に「ゲストで参加する」を出す**（`app.guest-login`）
- **起動時に営業中の状態を作る**（`app.demo-data`）
  厨房ボードが 3 列とも埋まり、在庫の残数・売り切れも映る
- **24 時間受付にする**
  実店舗の営業時間は 17:30〜翌 1:30。そのままだと昼間に見に来た方は何も注文できない
- **H2 のファイル DB を使う**（PostgreSQL を用意しない）
- **バックアップを止める**（消えて困るデータが無い）
- **H2 コンソールを閉じる**（誰でも触れる場所に DB の入口を出さない）

### 再起動でデータが消えるのは、むしろ好都合

無料ホスティングの多くは再起動でファイルが消える。
本来は困った性質だが、デモに限っては

- 誰かが注文を荒らしても、次の再起動できれいに戻る
- DB の契約も期限も要らない

消えて困るデータが最初から無いので、この割り切りが成立する。

## 3. Docker で動かす

リポジトリ直下の `Dockerfile` をそのまま使える。Render / Fly.io / Railway など Docker が使えるところならどこでも。

マルチステージにしてあるので、最終イメージに Maven もソースも入らない。
イメージが小さいほど起動が速く、**無料枠のコールドスタートが短くなる**。

メモリは `-XX:MaxRAMPercentage=70` を指定済み。
無料枠は 512MB のことが多く、指定しないと JVM がヒープを取りすぎてコンテナごと止められる。

---

## 4. 眠らせない

無料ホスティングは無通信が続くとサーバを眠らせる。
次に開いた人は 30〜40 秒待たされる。**採用担当は待たない。**

`/ping` が `ok` とだけ返す軽い入口なので、外から定期的に叩いて起こしておく。

> **アプリの中にタイマーを置いても無意味。**
> 眠っている間はそのタイマー自体が止まっている。自分で自分は起こせない。

### 何で叩くか

| | 良い点 | 注意 |
|---|---|---|
| **cron-job.org** | 無料・**時間帯を指定できる**（8〜17 時だけ、など） | おすすめ |
| UptimeRobot | 無料・落ちたらメールで知らせてくれる | 24 時間叩くので、Render の無料インスタンス時間を使い切りやすい |
| GitHub Actions | すでに使っているなら手軽 | private リポジトリだと**分数を使い切る**（1 回 15 秒でも 1 分として課金。10 分おきで月 1,800 分 ≒ 無料枠 2,000 分）。時刻も 5〜15 分ずれる。60 日放置で自動停止 |

**時間帯を絞るのが要点。** Render の無料インスタンス時間はアカウント全体で月 750 時間程度。
24 時間起こすと 1 サービスで月 730 時間になり、2 つ動かした時点で破綻する。
8〜17 時なら 1 サービス月 300 時間で、2 つでも収まる。

## 5. 公開前のチェック

- [ ] `APP_BASE_URL` が公開 URL（`https://`）になっている
- [ ] QR ページの URL が公開 URL になっている（見れば分かる）
- [ ] ログイン画面に「ゲストで参加する」が出ている
- [ ] ゲストで `/admin/settings` `/admin/staff` が **403** になる
- [ ] **管理者パスワードを変更した**（初期値のまま公開しない）
- [ ] リポジトリを public にするなら、**コミット履歴に鍵が無いか棚卸しした**

## 6. 訪問者がたどる道

```
ポートフォリオの GIF を見る
   ↓
「実際に触ってみる」を押す
   ↓
ログイン画面 →「ゲストで参加する」
   ↓
厨房ボード（すでに注文が並んでいる）
   ↓
サイドバー →「QRコード」
   ↓
「この卓のお客さま画面を開く」（別タブ）／ スマホで QR を読む
   ↓
注文する → 元のタブの厨房ボードに、その場で届く
```

タブを 2 つ並べれば、1 台の PC でも連携が体感できる。
スマホで QR を読んでもらえれば、実店舗とまったく同じ体験になる。
