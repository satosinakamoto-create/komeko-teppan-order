# このアプリの読み方 — 店主が自分で確かめるための手引き

コードを書かない人が、**中で何が起きているかを掴み、報告を検証できる**ようになるための文書。
2026-09-02 作成。

---

## 0. なぜこれを書いたか

「できました」と報告したあとに、実際は使えていなかったことが何度もあった。

| 報告 | 実際 |
|---|---|
| 税理士画面が完成しました | サイドバーに入口が無く、URL を手で打つ以外に開けなかった |
| 同上 | 既定が当月で、開いても空だった |
| Figma に書き出しました | 開くとトークンのページに着地し、画面が見つからなかった |
| 画面を作りました | 2 枚しか無く、サイドバーも無かった |
| 表をコンポーネント化しました | 塗りが無く、縞も入っていなかった |
| 見た目を揃えました | 表の右寄せが CSS の詳細度に負けて効いていなかった |

**共通する型は 1 つ。** 「操作が成功したこと」は確認したのに、
「**結果が使えるか**」を確認していない。
テストは通る。API は成功を返す。でも「辿り着けるか」「見えるか」は別の話。

この文書の後半は、その型を**あなたが**捕まえるための道具。

## 1. ひと言でいうと

**卓に貼った QR をお客さんが読む → スマホで注文 → 厨房に出る → 帰りにまとめて会計。**
これだけ。オンライン決済は無い（会計はレジ）。

そこに 2026 年から**仕入れ・在庫・原価**と**税理士の画面**が乗った。

## 2. 登場人物は 4 人

| 人 | 入口 | 見えるもの |
|---|---|---|
| お客さん | 卓の QR（`/t/…`） | メニュー・カート・伝票。ログイン不要 |
| 厨房 / ホール | ログイン（スタッフ） | 厨房ボード・会計・品切れ |
| 店長 | ログイン（管理者） | 上の全部 ＋ 商品・卓・売上・仕入れ |
| 顧問税理士 | ログイン（税理士） | 帳簿だけ。卓・QR・商品・スタッフは**見えない** |

権限の線引きは `config/SecurityConfig.java` の 1 ファイルに集めてある。
「誰に何を見せるか」で迷ったら、まずここを見る。

## 3. 注文が流れる道すじ

お金と時刻が絡むので、ここだけは順番を覚える価値がある。

```
① 卓の QR を読む            /t/{accessToken}
     ↓  ブラウザが「自分はこの卓」と覚える（TableContext）
② 人数を入れる              TableSession が 1 つ開く（＝伝票）
     ↓
③ メニューから選ぶ          カートはブラウザ側に貯まる
     ↓
④ 注文する                  Order が作られ、TableSession にぶら下がる
     ↓                      ★ このとき価格と税率を「写して」保存する
⑤ 厨房ボードに出る          受付 → 調理中 → 提供待ち → 受渡済
     ↓
⑥ 会計                      TableSession を CLOSED にする。売上はここで確定
```

**★ の「写して保存」が重要。** あとで商品の値段を変えても、
過去の注文の金額は動かない。だから売上が後から変わらない。

### 金額の計算は 1 か所だけ

```
小計          = キャンセル以外の注文の合計（税込）
テーブルチャージ = 単価 × 人数
深夜料金      = 深夜帯に出した注文 ＋ 深夜に着席していればチャージ、の合計 × 割増率
ご請求額      = 小計 + チャージ + 深夜料金
```

`TableSession.recalculate` の中だけ。ほかの場所で足し算をやり直さない決まりになっている。
**「金額が合わない」と感じたら、見る場所はここ 1 つ。**

深夜料金は**注文した時刻**で決まる。会計した時刻ではない。
22:55 と 23:05 の注文が同じ伝票に混ざり、後者だけ割増になる。

## 4. DB は 20 個の箱

「何を覚えているか」だけ掴めばいい。

**お店の基本（5）**
`shop_setting` 店の設定 / `category` カテゴリ / `menu_item` 商品 /
`option_group`・`option_choice` 選択肢（辛さ、大盛りなど）

**注文まわり（5）**
`dining_table` 卓 / `orders` 注文 / `order_line` 注文の明細 /
`order_line_option` 明細の選択肢 / `daily_counter` 注文番号の採番

**仕入れ・在庫（6）**
`purchase` レシート 1 枚 / `purchase_line` その明細 /
`ingredient` 食材 / `item_alias` 「エリンギ＝エリンギ 120円」の学習 /
`stocktake` 棚卸し / `recipe_line` レシピ（商品 1 個に食材を何 g）

**税まわり（3）**
`tax_rate_period` 税率の履歴 / `deduction_rate_period` 控除率の履歴 /
`journal_rule` 費目 → 勘定科目の対応表

**その他（1）** `staff_user` ログインする人

> ★ 在庫の数量はどこにも入っていない。
> 「直近の棚卸し ＋ 入庫 − 消費 ± 調整」で**毎回計算している**。
> 数字を持たないので、ズレが溜まらない。

## 5. コードの並び方 — 5 つの層

1 つの画面を出すのに、必ずこの順に通る。

| 層 | 何をする | 場所 | 数 |
|---|---|---|---|
| **画面** | 見た目。HTML | `templates/` | 50 |
| **窓口** | URL を受けて、下に頼む | `web/…Controller` | 42 |
| **段取り** | 業務のルール。計算・判断 | `service/` | 35 |
| **保管** | DB への出し入れ | `repository/` | 21 |
| **もの** | 商品・注文などの実体 | `domain/` | 36 |

**業務のルールは必ず「段取り」に置く**決まり。窓口には書かない。
だから「この計算どこ？」と聞かれたら答えは常に `service/` の中。

CSS は `static/css/app.css` の**1 ファイルだけ**。
色や寸法は先頭のトークン（変数）で決まっていて、そこを変えると全画面が変わる。

## 6. ★ 自分で確かめる方法

ここが本題。**コードを読まずに検証できる。**

### 6-1. 画面から確かめる（いちばん強い）

```powershell
.\tools\run.ps1
```
→ http://localhost:8080 が開く。実際に触る。これに勝る検証は無い。

**「できました」と言われたら、必ずこの 4 つを聞く。**

| 質問 | これで捕まる失敗 |
|---|---|
| **その画面、どこをクリックしたら行ける？** | 導線を作り忘れ（実際に起きた） |
| **データが 0 件のとき何が出る？** | 空で真っ白になる（実際に起きた） |
| **ログインしていない人が開いたらどうなる？** | 権限の穴 |
| **スマホの幅で崩れない？** | 表が横に溢れる |

1 つ目が最も効く。私が最も落としやすいのがここ。

### 6-2. テストを読む

このプロジェクトのテストは**日本語で名前が付いている**。中身を読む必要はない。

```powershell
.\tools\run.ps1 -Test
```

失敗すると、その日本語の名前が出る。
たとえば `★ 見た目は店舗管理と同じ` `深夜料金は注文時刻で決まる` のように。

**テストの一覧を眺めるだけで「何が守られているか」が分かる。**

```powershell
Get-ChildItem -Recurse src\test -Filter *.java |
  Select-String -Pattern '@DisplayName\("(.+)"\)' |
  ForEach-Object { $_.Matches.Groups[1].Value }
```

2026-09-02 に実行して 591 件。先頭はこんな並び。

```
税理士の画面
ログインしていなければ入れない
★ スタッフには帳簿が見えない（原価も控除率も全部見える画面なので）
★ 税理士には店舗運営の画面が見えない（卓・商品・スタッフ）
店長は税理士画面も見られる（何を渡しているか確認できる必要がある）
```

`★` が付いているのは「壊れると実害が出る」もの。

逆に言えば、**一覧に無いことは守られていない**。
「これテストある？」と聞けば、口約束か担保付きかが分かる。

### 6-3. 履歴を読む

```powershell
git log --oneline -20
```

コミットの題名は日本語で、**何をなぜ変えたか**を書く決まりにしてある。
本文（`git show <番号>`）には「なぜその案を採らなかったか」まで書いてある。

### 6-4. 「終わった」の定義を揃える

作業を頼むときに、**先に**これを言うと食い違いが減る。

> 「終わった＝**私が画面で触って確認できる**状態」

この 1 行があると、「テストは通りました」で報告を終えられなくなる。

## 7. 疑わしい報告の見分け方

| 報告の言い方 | 疑うポイント |
|---|---|
| 「テストが通りました」 | テストが**何を**守っているか。通ることと使えることは別 |
| 「実装しました」 | どこから辿り着ける？ |
| 「対応しました」 | 対応した**件数**は？ 全部？ 一部？ |
| 「同じにしました」 | 何と何を比べた？ 実測した？ |
| 「はずです」「と思います」 | 確かめていない。確かめさせる |

逆に、**次のような報告は信用できる**。

- 数字が入っている（「31 の表・153 列を突き合わせて、ずれ 0 件」）
- 確かめ方が書いてある（「ブラウザで計測した値と一致」）
- できていないことが書いてある（「厨房ボードは 1 画面に入る件数が減ります」）

## 8. 触ると危ないところ

| 場所 | なぜ |
|---|---|
| `TableSession.recalculate` | 金額の計算の中心。ここが狂うと請求額が狂う |
| `SecurityConfig` | 権限の線引き。緩めると税理士に店の運営が見える |
| `app.css` の `:root` と `.theme-snow` | **全画面**に効く（お客さん側を含む）。管理側だけ変えたいときは `.theme-desk` |
| 既存 13 テーブル | 本番の DB にすでにある。列の追加・削除は要注意 |

このへんを触る作業を頼むときは、**「テストは何本追加した？」**と聞くとよい。
