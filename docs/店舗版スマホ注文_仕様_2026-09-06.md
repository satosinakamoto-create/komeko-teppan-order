# 店舗版スマホ注文 — 仕様（2026-09-06 合意）

店舗のスマホ・iPad から、番号を選んで注文を受ける。

> **実装済み（2026-09-06）。入口は `/staff/order`。**
> 仕様の 1〜5 はすべて入っています。触るときの注意は末尾の「実装のメモ」を参照。

---

## ひとことで言うと

**お客さまの QR 注文と同じ仕組みで、入口だけ「QR を読む」→「番号を押す」に変えたもの。**

```
お客さま版:  QR を読む（＝卓が決まる）→ メニュー → カート → まとめて送る
店舗版:      番号を押す（＝卓が決まる）→ メニュー → カート → まとめて送る
```

メニュー・カート・売り切れの守り・選択肢の検証・厨房への流れは
お客さま版をそのまま使う。新しく作るのは入口の盤面と、下記の差分だけ。

---

## 決まったこと

### 1. 入口は番号の盤面。空席は人数を聞いてそのまま注文へ（A案）

全部の番号（テーブル＋カウンター札）を出す。

- **伝票が開いている番号** … 押したらそのまま品選びへ
- **空席の番号** … 「何名さまですか」→ 人数 → 伝票が開いて品選びへ。
  ご案内と最初の注文が 1 動線になる（着席時の「とりあえず生」が 1 回で済む）

**番号には人数・入店時刻・現在の金額を添える。**

```
札2   3名  19:20〜  ¥3,150
札5   2名  19:45〜    ¥960
テーブル1 （空席）
```

カウンターで組が隣り合っても、札は組の前に置いてあるので
店員は目の前の札を読んで押すだけ。一覧側の人数・時刻は
「いま話している 3 人組はこっちだ」という照合と、
離れた場所（厨房など）から入れるときの見分けに使う。

### 2. カートは選んだ札に紐づく。未送のまま札を替えようとしたら止める

お客さまのスマホは QR で卓に固定されるが、店舗のスマホは卓を渡り歩く。
「札2 に生ビール 2 つ積んだまま、呼ばれて札5 を開く」が起こる。

**送っていない品を持ったまま別の番号を押したら、確認を出す。**
「札2 に送っていない品が 2 点あります → 送る／破棄」。
黙って持ち越すと、札5 の伝票にビールが化ける。

### 3. まとめて 1 回で送る

画面に品を積んで、最後に「この内容で送る」。厨房には伝票 1 枚で出る。
着席時の 5 品注文が伝票 5 枚に割れない（1 品ずつ即送信の
既存 `/hall/bills/{id}/orders/new` はそうなっていた）。

### 4. 時価は注文受付時に金額を入れる（会計時ではない）

店員は席で口頭で金額を伝えてから注文を受けるので、その場で入れる。

会計時入力を採らなかった理由:

- **お客さまの伝票画面が一晩中違う金額になる。** 伝票は各自のスマホで
  数秒ごとに更新される。¥0 のまま載せると、合計 ¥5,100 を見ながら飲んで
  レジで ¥11,900 と言われることになる
- **入れ忘れが ¥0 のまま通り抜ける。** `placeByStaff` の「時価は金額必須」の門は
  この取りこぼしを塞ぐためにある。会計時入力はその門を自分で開け直すこと
- **「注文時点の価格をスナップショット」の大原則（CLAUDE.md）と喧嘩する。**
  深夜料金も注文時刻の金額で計算される

**画面では「金額を入れるまで、その品を積めない」形にする。**
送る段で断られるのではなく、入口で入れられない。
カートに ¥0 の時価が一瞬でも存在しなければ、送り忘れも表示のずれも起きようがない。

判断の中身は `placeByStaff` と同じ:
時価（価格 0 以下）は金額必須・上限 10 万円、ふつうの品への値付けは拒否、
時価の品の「売り切れ」登録は通す（あれは「値段未定」の意味）。
画面の必須指定は近道でしかなく、本当の門はサーバ側（開発者ツールで外せるため）。

### 5. ログインは既存の STAFF アカウント。端末は基本 1 人固定

**新しく作るものは無い。** アカウントは管理画面 → スタッフで人数分作れる。
ログインは端末に残り続け、ログアウトすれば交代できる。
やることは新しい画面にログアウトを置くことだけ。

`placedBy` に入力者が残る（時価は人が金額を決めるので、
誰が決めたかを追える必要がある。V11 で導入済み）。

## 実装のメモ（2026-09-06）

### どこに何があるか

| | |
|---|---|
| 盤面・送信の口 | `web/staff/StaffOrderController`（`/staff/order`） |
| 画面 | `templates/staff/order-board.html` / `order-guests.html` / `order-switch.html` |
| 金額の門 | `service/StaffPriceRule`（**判断はここ 1 か所**） |
| カートに積む | `CartService#addByStaff` |
| まとめて送る | `OrderService#placeFromStaffCart` → `place(cart, sessionId, note, placedBy)` |
| 店員かどうかの印 | `TableContext#staffMode`（`bindByStaff` で立つ） |
| 見た目 | `app.css` 31-9 節 |

### ★ 触るときに知っておくこと

- **卓の入れ物（`TableContext`）はお客さまと共有しています。**
  別に作ると、メニュー・品選び・カートの 3 画面が「どちらを見るか」を
  自分で判断することになり、片方だけ直したときにずれます。
  違うところだけ `staffMode` で分けています。
- **`CartService#refresh` は時価の品を特別扱いします。**
  送信の直前に走る洗い替えで、ふつうならマスタ価格（時価は 0 円）に戻します。
  そのままだと店員が入れた 6,800 円が<b>送信の瞬間に消え</b>、
  さらに「売り切れ」として落とされます。どちらも例外が出ないので、
  お客さまの伝票で初めて分かります。
  判定は「マスタ 0 円 かつ カートに金額あり」（`pricedByStaff`）。
- **`OrderService#place` は分岐しません。** 記録する `placedBy` が違うだけで、
  営業時間の確認も、お会計との排他も、売り切れの扱いもお客さまと同じです。
- **金額の門は 2 か所から呼ばれます**（伝票の 1 品ずつ入れる口と、カートに積む口）。
  `StaffPriceRule` を通さない道を作ると、そちらから ¥0 が素通りします。
- **`/staff/**` は見学者（GUEST）に開けていません。** ここから送った注文は
  本物の伝票に載り、時価には金額まで入れられます。
  接続元の制限（`StaffZoneIpFilter`）にも入れてあります。
