# レシピの「その他材料費」— 設計（2026-09-16）

## なぜ作るか

店主の指摘：

> レシピ原価表で食材を g 数しか編集できない。食材入れずに原価だけ入れて保存できないの？
> 細かく食材の g 数だけ入れても毎年毎月でも食材費って変動するじゃん

いまのレシピは `食材 + g 数` の行しか持てません。**原価を知りたいだけの商品にも、
全部の食材を g 数で登録させている**のが問題です。油・塩・ソースのように
量を測らないものもあり（設計文書の未解決質問⑦）、80 品すべてを登録するのは現実的ではありません。

**この設計で解決すること**

- 食材を 1 件も入れずに、金額だけで原価を入れて保存できる
- 主要な食材だけ g 数で入れて、残りはまとめて金額で置ける

**この設計で解決しないこと（重要）**

- **g 数の入力そのものは楽になりません。** 「g 数を任意にする」変更であって、
  入力を簡単にする変更ではありません
- **在庫を自動で減らしたい商品は、結局 g 数が要ります。** 金額だけの商品は
  売れても在庫が減りません。使い分けになります

## 採らなかった案

### 案B：レシピ行の食材を空にできるようにする

最初に検討した形。`recipe_line.ingredient_id` の NOT NULL を外す。**却下。**

影響範囲調査（2026-09-16）で、**静かに壊れる**ことが分かったためです。

- `RecipeLineRepository.findAllWithRelations` が `join fetch r.ingredient` ＝ **内部結合**。
  食材なしの行は例外も警告も出さずに結果から消え、
  **原価表と消費計算の入力から同時に落ちる**。「保存したのに出てこない・消せない」行になる
- 同じ内部結合が `findByMenuItem`（レシピ編集画面）にもある
- `findByIngredient`（食材を止める前の巻き添え確認）から漏れる
- NPE が 5 箇所：`RecipeService:109`・`ConsumptionService:90`・`RecipeService:259`・
  `recipe-edit.html` の 3 箇所
- 本番は `ddl-auto: validate` なので、列とフィールドを別々に変えると起動不能

### 案C：食材テーブルに番兵行（ダミーの「その他材料費」食材）を 1 件入れる

店主の案。`costOverride = 1` にすれば `qty × 1円` で金額になり、計算は合います。**却下。**

特別扱いが 3 箇所要るためです。

1. 在庫一覧に出さないため `active=false` が要る（放置すると在庫がマイナスに増え続け、
   永久に赤い行が居座る）
2. ところが `active=false` にすると `levels` に入らず**単価を引けなくなる**ので、
   `RecipeService` に「一覧に無ければ固定単価を直接読む」分岐が要る
3. 同じ理由でレシピ編集の食材ドロップダウンにも出ないので、そこにも例外が要る

加えて、金額を `qty_per_item`（グラム数の列）に入れることになります。

> **このプロジェクトは一度、同じ形を明確に断っています。**
> 削除した `IngredientCategory` のコメント：「『その他』を既定にすると、分類し忘れた食材と
> 本当にその他な食材が同じ棚に混ざります」。ダミーを混ぜると本物と区別が付かなくなる、
> という判断です。今回も食材テーブルに食材でないものが 1 件混ざります。

なお **性能・インデックスは判断材料になりません。** 食材検索は DB ではなく
Java のメモリ上で絞り込んでおり（`InventoryIngredientController.index`）、
食材 50 件・商品 80 件の規模では番兵行 1 件の差は測れません。
採否の理由は**保守性だけ**です。

## 採る案：商品ごとに「その他材料費」を別に持つ

レシピ行には**一切触りません。** 在庫モジュール側に小さなテーブルを 1 つ足します。

### データ

`recipe_other_cost`（Flyway `V18`）

| 列 | 型 | 制約 | 意味 |
|---|---|---|---|
| `id` | BIGINT | PK, IDENTITY | |
| `menu_item_id` | BIGINT | NOT NULL, **UNIQUE**, FK → `menu_item` | 商品 1 つにつき 1 件 |
| `amount_including_tax` | INT | NOT NULL, **> 0** | 円・**税込** |
| `memo` | VARCHAR(100) | NULL 可 | 「ソース・青のり・かつお節」など |

- **金額は `int`（円）。** `double` / `float` 禁止の規約どおり
- **税込で持つ。** 価格は税込保持の規約に合わせる。税抜は `TaxCalculator` で割り戻す
  （税率をここに書かない／自前計算しない、の規約）
- **UNIQUE を張る。** 1 商品に 2 件あると、どちらを足すかが決まらない
- **0 と空欄は行ごと削除。** 0 円の行を残すと「その他材料費を検討した結果 0 円」と
  「まだ入れていない」が区別できなくなる（未分類を null で表したのと同じ理由）
- **マイナスは禁止。** 入れると原価が減って原価率が嘘になる。
  オプションの追加料金を 0 円以上に閉じているのと同じ判断

`app.inventory.enabled=false` で在庫モジュールを切ったとき、既存 13 テーブルに痕跡が残りません。
「既存テーブルに列を足さない」という Step 1〜3 からの約束を維持します。

### 計算

`RecipeService.costOf` に 1 項足すだけです。

```
原価（税込） = Σ レシピ行の原価 + その他材料費
原価（税抜） = Σ レシピ行の原価（税抜） + TaxCalculator.netAmount(その他材料費, 税率)
```

**`lines.isEmpty() ? null : cost` の条件を変えます。** いまはレシピ行が 0 件なら原価を
null にしていますが、その他材料費があれば原価は出せます。

```
原価が null になるのは「レシピ行が 0 件 かつ その他材料費が無い」ときだけ
```

**`unknownCostCount` には影響しません。** その他材料費は人が入れた確定値で、
「単価が分からない食材」とは種類が違います。混ぜると
「原価が足りていない」警告の意味が濁ります。

### 在庫（無変更）

`ConsumptionService` も `RecipeLineRepository` も `StockService` も触りません。
**金額行という概念が `recipe_line` に存在しないので、消費計算からは原理的に見えません。**

これが案A を選ぶ最大の理由です。除外を書く必要がないので、除外の書き忘れも起きません。

### 「レシピ登録済み」の扱い — 2 つの意味を分ける

その他材料費だけ入れた商品を「レシピ登録済み」とみなすかどうか。**用途ごとに分けます。**

| 使うところ | 判定 | 理由 |
|---|---|---|
| 原価表・商品一覧の原価列 | **原価あり**として扱う | その他材料費があるので原価は出る |
| 在庫の「あと◯営業日が甘い」警告 | **未登録のまま**出し続ける | 食材が紐づいていない＝売れても在庫が減らない。予測は本当に甘い |

`RecipeService.menuItemsWithoutRecipe()`（在庫警告側）は**変更しません。**
変えるのは原価の表示側だけです。同じ「登録済み」でも意味が違うので、
1 つの判定に寄せないこと。

### 画面

- **レシピ編集**：材料の行の下に「その他材料費（任意）」の金額欄とメモ欄を 1 組。
  既存のフォーム送信の流れに乗せる（JavaScript を増やさない）
- **原価の内訳**：材料の行の最後に「その他材料費 ◯円」を 1 行出す。
  合計だけ変わって内訳に出ないと、どこから来た金額か分からなくなる
- 金額表示は `#numbers.formatInteger(v, 1, 'COMMA')`
- 更新系の POST は `redirect:` で返す（PRG 厳守）。フォームは `th:action="@{/...}"`

## テスト（先に書く）

| # | 何を守るか |
|---|---|
| 1 | その他材料費だけで原価と原価率が出る（レシピ行 0 件） |
| 2 | レシピ行と混ざったとき、合算される（税込・税抜の両方） |
| 3 | **在庫の消費計算に影響しない**（回帰。その他材料費を入れても残量が変わらない） |
| 4 | マイナス・0・空欄の扱い（保存されない／行が消える） |
| 5 | 1 商品に 2 件作れない（UNIQUE） |
| 6 | レシピ行 0 件かつその他材料費も無い商品は、いままでどおり原価 null |

3 番が一番大事です。**この設計の前提そのもの**なので、壊れたら気づける必要があります。

金額計算は壊すと実害が出るため、`@DisplayName` は日本語で、
何を守っているかをコメントに書きます（規約どおり）。
