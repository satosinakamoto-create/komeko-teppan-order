## 🔴 CRITICAL（1件）

### C-1. キャンセル経路が伝票ロックを取らず、closeSession と競合すると会計済み伝票が黙って OPEN に戻る

`src/main/java/jp/komeko/order/service/OrderService.java:440`

T1 = `cancelByStaff` / `cancelByCustomer` が注文と伝票（OPEN）を読む
→ T2 = `closeSession` が FOR UPDATE を取り締めてコミット（請求額確定・レジで収受）
→ T1 の `requireBillStillOpenForCancel` はメモリ上の古い OPEN を見て通過し、
`order.cancel` + `refreshSessionOf` で再計算
→ `restoreStock` の `flushAutomatically=true` で flush される `UPDATE table_session` は全カラム書き
（`@DynamicUpdate` なし・`@Version` なし）なので `status=OPEN, closedAt=null, closedBy=null,
減額後の金額` で T2 の会計を丸ごと上書き。

**エラーは一切出ません。** 締めたはずの伝票が減額されて開き直る = 会計証跡の破壊。
レジで受け取った額と記録が食い違います。

根拠: `OrderService.java:378-391`（`cancelByStaff` はロック無しの `findWithLinesById`→check→refresh→restore）、
`440-446`（check は読み取りのみ）、`497-502`（`refreshSessionOf` が伝票を再計算=dirty 化）、
`TableService.java:254`（`closeSession` 側だけ `findWithLockById`）、
`TableSession.java:46-69`（`@Version`/`@DynamicUpdate` なし→全カラム UPDATE）、
`MenuItemRepository.java:99`（`flushAutomatically=true` が cancel の途中で伝票 UPDATE を発行）。

**`src/test` 全体に `Thread` / `CountDownLatch` / `ExecutorService` が 0 件で、この並行系は未テスト。**

## 🟠 MAJOR（12件）

### M-1. `spring.main.lazy-initialization=true` で ProductionSafetyGuard が丸ごと無効化される ★実機で突破を確認済み

`src/main/java/jp/komeko/order/config/ProductionSafetyGuard.java:30`

`SPRING_PROFILES_ACTIVE=prod,demo` に `SPRING_MAIN_LAZY_INITIALIZATION=true`
（または `JAVA_OPTS` の `-Dspring.main.lazy-initialization=true`）が加わると、
誰にも注入されていない guard Bean は**一度も生成されず**、一方 ApplicationRunner は lazy でも必ず実行されるため
`DemoDataSeeder` が prod DB に架空の伝票・注文を書き込み、店舗設定を 24 時間受付に書き換え、
`/login` に「ゲストで参加する」が出ます。

**実測**: ベースライン（prod,demo）は `IllegalStateException` で正しく中止。
`SPRING_MAIN_LAZY_INITIALIZATION=true` を足すと起動成功し、
シーダーのログ「3 卓ぶんの伝票を作成」「デモのため 24 時間受付に切り替えました」を確認、
curl で `/demo`=302・`/login`=200・「ゲストで参加する」表示を確認。

lazy-init は **Render のコールドスタート短縮策として足されやすい設定**です。
最小修正は `@Lazy(false)` 付与（グローバル lazy-init は `@Lazy(false)` の Bean を除外する）か、
`EnvironmentPostProcessor` 化。

### M-4. お客さま側 `POST /t/{token}/start` が既存 OPEN 伝票の人数を無条件・無ログで上書きし、チャージが黙って減る

`src/main/java/jp/komeko/order/service/TableService.java:150`

6 名で来店しスタッフが 6 名でご案内（チャージ ¥450×6=¥2,700）。
遅れて QR を読んだ 1 人のスマホに残っていた**古い人数選択画面**から「1 名」を送信すると、
`openSession` の既存伝票ブランチが `setGuestCount(1)` を実行し refresh で再計算。
**チャージは ¥450 に減り、ログは 1 行も出ず**（「伝票を開きました」は新規作成時のみ）、ホールへの通知もありません。

悪意ケースでは、卓に着いた客が同一セッションの CSRF トークンで `/t/{token}/start` を直接 POST すれば
任意タイミングで人数を 1 に落とせます（`/t/**` は permitAll、`SecurityConfig.java:121-123`）。

### M-5. 5:00 切替で「会計済みだが未調理」の注文が厨房ボードから消える

`src/main/java/jp/komeko/order/repository/OrderRepository.java:51`

朝まで営業で 4:50 に会計を締めた卓に RECEIVED/COOKING/READY の注文が残っている状態で 5:00 を跨ぐと、
その注文は `businessDate=前営業日` かつ `session=CLOSED` となり、
`findKitchenBoardOrders` の「businessDate 一致 or session OPEN」のどちらにも該当せず**全レーンから消えます**。
請求は済んでいるので金は消えませんが、厨房が焼くべき品の存在を知り得なくなります。

### M-6. 同一注文への並行キャンセル（厨房×お客さま）で在庫が二重に復元される

`src/main/java/jp/komeko/order/service/OrderService.java:381`

両トランザクションとも `status=RECEIVED` を読み `alreadyCanceled=false` と判定 → 両方が `restoreStock(+qty)` を実行。
`stockRemaining` が実消費 1 に対し +2qty 戻る → 画面に存在しない在庫が出て**数量限定品を売り越します**。
`restoreStockOf` の Javadoc(466-470) 自ら「二重に戻すと売り越えの原因」と警告している保証が並行時に破れます。

### M-7. キャンセルと「焼きはじめ」の並行実行で、キャンセルが消滅し在庫だけ復元されたまま請求に復活する

## 根本原因は 1 つに集約できます

C-1 / M-3 / M-6 / M-7 は全て同じ構造です。

- `Order` にも `TableSession` にも **`@Version` が無い**（grep で 0 件）
- `@DynamicUpdate` も無いので、コミット時に**全カラムを上書き**する
- ロックは `placeOrder` ↔ `closeSession` の 1 ペアにしか無い
- **並行系のテストが 1 件も無い**（`Thread`/`CountDownLatch`/`ExecutorService` が 0 件）

つまり「読んで、チェックして、書く」の間に他トランザクションが割り込む窓が、
伝票を変更する全経路に開いています。`@Version` による楽観ロックを
`Order` と `TableSession` に入れるのが最小で最も効く対処と思われますが、
**まず 1 件ずつ検証してから**着手してください。
